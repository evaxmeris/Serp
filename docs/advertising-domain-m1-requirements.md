## 一、术语与口径定义

| 术语 | 定义 | 说明 |
|------|------|------|
| 投放词（Targeting） | 广告后台实际投放的关键词/商品定向实体 | 组合粒度 = **投放词 × 匹配类型**（如 `breast enhancement cream × EXACT`） |
| 客户搜索词（Search Term） | 用户真实输入的搜索词 | 搜索词报告按此聚合 |
| 搜索词报告 | 亚马逊「衡量和报告 → 搜索词报告」导出 | 含客户搜索词、CPC；**不含 bid 列、不含状态列** |
| Targeting 报告（投放报告） | 亚马逊「查看所有模板 → Targeting（投放）」导出 | **投放词维度唯一真相**：含目标竞价(bid)列、投放状态列、全部投放组合（含 0 点击） |
| L1 语义族 | 品类词根 × 诉求词根聚类（如「臀·紧致」「胸·合规丰盈」） | 族级决策的最小单位 |
| L2 完全重复 | normalize 后完全一致（词序/单复数/同义词根） | 重复词只有「关闭」一个处置 |
| 同词多匹配 | 同一投放词开了多层匹配 | 保留 EXACT + 至多 1 个探索层 |
| 双标准 | 关闭/否定的唯一数据判据：`0单 且 (点击≥否定阈值 或 花费≥成本容忍值)` | 阈值**每轮动态计算，禁止硬编码** |
| 否定阈值 | 既有出单词「点击/单」中位数 × 2 | v19 实算 34 点击 |
| 成本容忍值 | 1.5 × 客单价 | v19 实算 $23.76 |
| 盈亏平衡 ACoS | ≈ 毛利率（本账户 40%） | ACoS > 平衡点 = 亏本卖 |
| 批量操作表（Bulk Operations） | 上传回亚马逊批量执行的电子表格 | 33 列标准模板，Sheet 名 `Sponsored Products Campaigns` |
| Bulk 三件套 | Campaign ID + Ad Group ID + Keyword/Product Targeting ID | Targeting 报告自带，用于执行定位 |
| 僵尸词 | ENABLED 且有展示但 0 点击的投放词 | 展示≥50 关闭，<50 留观 |

### 1.1 口径铁律（贯穿全系统的判断依据）

1. **决策档位以 Targeting 报告为准**：凡投放词维度判断（是否出单/某层是否零转化/是否关层/调价档位），一律用 Targeting 报告数据。v17 实证：同一词 EXACT 搜索词报告 ACoS 39.6% vs Targeting 40.4%，档位反转。
2. **竞价层级判断用 bid，禁止用 CPC**：搜索词报告只有 CPC（实际扣费，受第二价格拍卖影响低于 bid），不能用于层级倒挂判断。bid 来源 = Targeting 报告「目标竞价」列；无 bid 数据时输出「需用户从后台核对」清单，**禁止用 CPC 冒充**。
3. **双报告缺一不可**：单用搜索词报告无法做竞价调整（无 bid 数值）与状态核对。无 Targeting 报告时，系统不得产出 bid 调整/层级核对结论，只能产出「提示 + 待核对清单」。

## 二、业务目标与范围

### 2.1 业务问题（现状痛点）

| 痛点 | 现状 | 后果 |
|------|------|------|
| 广告数据分散 | 搜索词报告/Targeting 报告/竞价设置散落在亚马逊广告后台，导出一次 30 天窗口 | 无法跨期对比、复盘无据 |
| 决策无系统沉淀 | 决策引擎（Python v20）在 `~/clawd/amazon-ads-optimizer` 独立运行，结果存在本地文件 | 决策历史不可追溯、10 轮纠正出的规则无系统固化 |
| 执行靠人工 | 分析结论要手工逐条到后台改 bid/暂停/加否定 | 100+ 组合逐条点击不现实，易错易漏 |
| 数据敏感无管控 | 广告花费/销售是核心经营数据 | 需要权限分级 |

### 2.2 业务目标（M1 可达成）

1. **G1 数据集中**：双报告上传落库，原始数据 + 文件归档可追溯，报告历史可查。
2. **G2 决策系统化**：v20 决策引擎规则 100% 固化进系统，一键跑批产出族级总览/关闭矩阵/否定清单/拓词/层级核对/执行摘要。
3. **G3 执行闭环**：勾选执行清单 → 下载亚马逊批量操作表（Bulk 33 列）→ 后台批量执行。M1 下载执行，M2 API 自动执行（数据获取层预留）。
4. **G4 权限管控**：广告数据按角色分级可见（admin/sales 可操作，viewer 只读或不可见）。
5. **G5 可追溯**：每条建议可追溯到原始报告数据行与依据文字，用户逐条核对无障碍。

### 2.3 范围

- **范围内（M1）**：投流优化中心（上传→分析→展示→勾选→批量表下载）+ 站点管理（marketplace 配置 + 广告账户绑定）+ 「亚马逊运营」一级菜单（库存/补货/看板占位）。
- **范围外（M1 明确不做）**：Ads API 自动拉取/自动执行（M2）、FBA 库存对接（M3）、补货计划（M4）、TikTok 广告（M5）、跨域看板（M6）。数据看板与多站点切换为 P2（见 §3.3）。

### 2.4 系统边界与集成方式

- **决策引擎**：复用 Python v20 引擎（`services/amazon-ads-engine/analyze_cli.py`），Node 侧子进程调用 + JSON 文件交换（简单、无端口管理、失败可重试）。**不重写引擎逻辑**——v20 已 10 轮用户验证。
- **数据获取层**：业务层（解析→引擎→决策→展示/执行）与数据获取解耦，M1 用 `ManualFetcher`（手动上传），M2 切 `ApiFetcher`（Ads API，审批 2-4 周后），业务层零改动。

## 三、功能需求（P0/P1/P2）

> 需求编号规则：`REQ-<域>-<序号>`。优先级定义：P0 = M1 必须交付（不可裁剪）；P1 = M1 应交付（资源不足可顺延，但不影响核心闭环）；P2 = M1 可后置（预留数据与接口即可）。

### 3.1 P0 功能需求（核心闭环）

#### REQ-ADS-001 双报告上传与解析

- **001-1** 支持上传 2 份报告：搜索词报告（xlsx/csv）+ Targeting 报告（csv/xlsx），multipart 一次提交或分次提交均可。
- **001-2** 上传时必填：广告账户（下拉，来自站点管理）、报告日期范围（startDate/endDate）。系统校验日期与报告内数据窗口一致（不一致给警告，不阻断）。
- **001-3** 解析能力（v20 已适配，必须复用）：
  - xlsx inlineStr 单元格解析（亚马逊 xlsx 用 inlineStr 而非 sharedStrings）；
  - Targeting CSV 新版列名自动探测（`投放方案/投放匹配类型/投放状态/目标竞价/总成本/购买量/展示量/点击量/销售额` 与旧版投放报告列名兼容）；列名随站点/语言变化时，解析器保留「列名探测 + 映射」能力，探测失败给出明确错误（列名风险提示见 §8 R3 与 REQ-ADS-005-5）；
  - 数值清洗：剥离 `%`/`$`/千分位；ID 列 `="123"` 自动去壳；
  - 中文导出列名映射（投放=targeting、匹配类型=matchType、客户搜索词=customerSearchTerm、花费=spend、7天总销售额=attributedSales7d、7天总订单数=attributedUnitsOrdered7d）。
- **001-4** 解析后落库 `AdReport`（原始数据行 rawRows + summary 账户总览 + 文件归档 filePath），原始文件永久保留。
- **001-5** 上传前校验报告类型与内容：文件可读、必填列存在、行数>0。失败返回明确原因（见 §6.2 异常流程 E1）。
- **001-6** 双报告口径一致性校验：同一账户同窗口内，Targeting 报告花费/订单应 ≥ 搜索词报告（Targeting 收录全部投放词含 0 点击，搜索词报告仅收录 ≥1 点击的词）。偏差 >15% 时给出警告（v17 实测两报告偏差在 5-15% 属正常，但需提示用户确认窗口一致）。

#### REQ-ADS-002 v20 决策引擎分析（跑批）

- **002-1** 对已上传报告执行 v20 引擎全流程：账户总览 → 双维度聚合 → L1 语义族聚类 + L2 重复识别 → 状态核对（Targeting 报告自动）→ 系统处置（双标准）→ 增量拓词 → 分层架构（bid 自动读取）→ 竞价调整 → 层级复核 → 关闭预演。**规则明细见 §4，全部纳入 P0。**
- **002-2** 引擎调用：Node 子进程执行 `analyze_cli.py --search <file> --targeting <file> --out <out.json>`，超时 120s，失败自动重试 1 次，stderr 与 exit code 全量记录。
- **002-3** 引擎输出 JSON 契约（固定，UTF-8）：`account / families / closeMatrix / negateList / expandTable / layerCheck / summary / version`，逐字段校验 `{ok:true}` 才落库；`{ok:false}` 按 §6.2 E2 处理。
- **002-4** 结果落库：`AdRecommendation`（v20 快照，Json 字段）+ `AdKeyword` 决策字段（familyL1/duplicateOf/action/actionBid/actionReason/acos/orders/spend/clicks/impressions/ctr/reportId）。
- **002-5** 参数可配置（引擎 CLI 参数透传）：盈亏平衡 ACoS（默认 40%）、否定阈值/成本容忍值（默认动态计算，不硬编码——见 §4.3）。
- **002-6** 同一报告可重复分析（引擎升级后重跑），生成新的 AdRecommendation 版本，不覆盖旧版。

#### REQ-ADS-003 结果展示（族级总览 / 关闭矩阵 / 否定清单 / 拓词 / 层级核对）

投流优化中心页面，自上而下分区展示（全部可读自 AdRecommendation 快照）：

- **003-1 账户总览卡片**：花费 / 销售 / 订单 / ACoS（vs 盈亏平衡点）/ CVR / 客单价；ACoS 超平衡点标红。
- **003-2 族级总览表**：每个 L1 族一行（**每族必须有处置结论**，不得遗漏），列 = 族名 / 花费 / 订单 / ACoS / 处置结论（加投/收缩/重度收缩/整族关/待观察/不拓等）；Tabs 按「全部 / 出单族 / 风险族 / 待关闭」分组 + 数量徽章；族行可展开查看成员投放组合。
- **003-3 关闭矩阵表**：全量投放组合逐条（**不遗漏**），列 = 投放词 / 匹配类型 / 点击 / 花费 / CTR / CPA / 当前 bid / 状态 / 依据文字 / 建议动作；动作列可勾选（见 REQ-ADS-004）。
- **003-4 否定清单表**：搜索词维度，列 = 搜索词 / 原因 / 依据文字；**否定允许依据仅三类**：①合规风险词 ②双标准达标 ③明显不相关（竞品/非本品类商品，相关性判定，v19 实证 1 条）（口径与 §4.4 一致）。
- **003-5 拓词结论表**：每族一行拓词结论（★开 BROAD / ★收割 / 换变体策略 / 小预算试探 / 样本不足 / 不拓）+ 增量搜索词明细（增量词文本、当前由谁捕获、点击/出单）。
- **003-6 层级核对区**：a) 竞价层级倒挂警告列表（EXACT≤PHRASE 或 PHRASE≤BROAD，用 bid 判断）；b) 探索层系数体检表（每族每层实际 bid 系数 = 探索层 bid ÷ EXACT bid，与规范 0.75/0.50 对比，偏高标红）；c) 调价后层级复核结果（倒挂数必须为 0，见 §4.7）。
- **003-7 执行摘要条**：关闭 X 个组合 / 关闭 X% 花费 / 关闭后 ACoS 预演 / 是否还需叠加调价或修 listing 的说明。
- **003-8 所有表格遵循现有 UI 铁律**：CSS 变量、骨架屏、Toast、分页、fade-in；数字与引擎 JSON 一致，禁止二次换算造成偏差。

#### REQ-ADS-004 执行清单勾选

- **004-1** 关闭矩阵/否定清单/拓词（新建精准）/层级核对（改价）中每条建议动作默认携带引擎建议值，用户可勾选/取消。
- **004-2** 用户可手工覆写单个建议：改动作类型或改数值（如改 bid 值），覆写后该行标注「手工修改」，批量表以其覆写值为准。覆写需权限（§5）。
- **004-3** 勾选状态与覆写持久化（绑定 AdKeyword/AdRecommendation），刷新/重进不丢失。
- **004-4** 执行清单汇总区：已勾选动作分类计数（关闭 n / 改价 n / 否定 n / 新建 n），与批量表行数一致。

#### REQ-ADS-005 批量操作表下载

- **005-1** 按勾选清单生成 Bulk Operations xlsx（exceljs），Sheet 名 `Sponsored Products Campaigns`，Product 列固定 `Sponsored Products`，33 列标准英文模板。
- **005-2** 三类操作行（v18.1 已验证格式）：
  - 关闭：Entity=Keyword / Product Targeting，Operation=Update，填 Bulk 三件套 + `State=paused`（**禁止同时填 Bid**）；
  - 改价：Operation=Update，三件套 + `State=enabled` + `Bid=层级约束后的最终值`（两位小数；**不是纯按 ACoS 的数值**，见 §4.7）；
  - 否定：Entity=Campaign Negative Keyword，Operation=Create，Campaign ID + Keyword Text + `Match Type=negativeExact` + `State=enabled`。风险词输出两行：关闭 + 活动级否定。
- **005-3** Entity 判定：匹配类型 ∈ {EXACT/PHRASE/BROAD} → Keyword（Match Type 小写 exact/phrase/broad）；`TARGETING_EXPRESSION_PREDEFINED` / `TARGETING_EXPRESSION` → Product Targeting。
- **005-4** 生成前自检（4 项必须全为 0，任一非 0 拒绝生成并报错）：Update 行缺 Campaign/AdGroup ID=0；Entity=Keyword 缺 Keyword ID=0；State 非 paused/enabled=0；`State=paused` 与 Bid 并存=0。
- **005-5** 下载时伴随交付 `批量表使用说明.txt`：备份（先下载后台现有表格作回滚备份）→ 核对列名 → 上传 → 预期效果 → 回滚方法。执行风险最高的一步必须给指引。
- **005-6** 中文投放词加否定被拒的风险提示（美国站单行失败不影响整表、上传后下载处理结果核对成功行数）写入使用说明。

#### REQ-ADS-006 站点管理（marketplace + 广告账户绑定）

- **006-1** 站点（marketplace）配置：预设亚马逊主流站点（US/CA/BR/UK/DE/FR/ES/IT/JP），含 marketplaceId（如 US=ATVPDKIKX0DER）、货币、广告端点（US=`advertising-api.amazon.com`，EU=`advertising-api-eu.amazon.com`）；站点列表可增删改（P0 提供默认集 + CRUD）。
- **006-2** 广告账户（AdAccount）绑定：账户名 / marketplaceId / 外部 profileId / 广告 API 凭据（clientId / clientSecret / refreshToken，**加密存储**，见 §9.2）/ 可选关联订单域 PlatformAccount。
- **006-3** 凭据字段后端返回一律脱敏（只回显后 4 位）；写入后不可回读明文。
- **006-4** 账户启停开关（isActive）；`platformCode + marketplaceId` 唯一。
- **006-5** M1 账户凭据仅存储（审批通过后 M2 才使用）；页面注明「API 凭据用于 M2 自动拉取，当前阶段仅手动上传报告」。

### 3.2 P1 功能需求

#### REQ-ADS-007 数据获取层抽象（ManualFetcher / ApiFetcher 预留）

- **007-1** 定义统一数据获取接口 `ReportFetcher`：`fetchReport(reportType, dateRange) → AdReport` + `fetchSettings() → 当前 bid/状态快照`。业务层只依赖接口。
- **007-2** M1 实现 `ManualFetcher`：读取上传文件 → 落 AdReport（source=MANUAL_UPLOAD）。
- **007-3** 预留 `ApiFetcher` 接口签名与配置位（source=API），M2 实现：`POST /reporting/reports` 异步建报告 → 轮询 → 下载 → 落同一 AdReport 表；`GET /sp/keywords` 实时读 bid/状态供层级核对（比报告更实时）；`PUT /sp/keywords` + `POST /sp/negativeKeywords` 程序化执行（dry-run 默认 + 二次确认 + 单批上限 50）。
- **007-4** 报告来源（MANUAL_UPLOAD / API）字段贯穿展示，历史列表可筛。

#### REQ-ADS-008 报告历史

- **008-1** 报告历史列表：账户 / 报告类型 / 日期范围 / 来源 / 文件 / 行数 / 上传时间 / 关联决策版本；可下载原始文件归档。
- **008-2** 历史报告可重新触发分析（引擎升级后重跑），生成新决策版本。

#### REQ-ADS-009 决策历史对比

- **009-1** 决策快照列表：每份 AdRecommendation 一条（版本 / 时间 / 报告引用 / 执行摘要快照）。

### 3.4 数据模型需求（供实现对齐，需求级约束）

> 新表（5 张）：`AdAccount / AdCampaign / AdKeyword / AdReport / AdRecommendation`。需求级约束如下，字段级设计以 Arch 文档为准。

| 表 | 需求级约束 |
|----|-----------|
| AdAccount | `platformCode`(默认 amazon) + `marketplaceId` 唯一；广告 API 凭据字段独立于订单域 PlatformAccount（广告凭据 ≠ 订单凭据，不侵入订单域）；凭据加密 |

| AdKeyword | **核心资产**。组合粒度=投放词×匹配类型；必须含 Bulk 三件套（`campaignId/adGroupId/externalId`）；v20 决策字段（familyL1/duplicateOf/action/actionBid/actionReason/reportId）；`actionReason` 为**必填**（每条建议必须有依据文字，§8.1） |

## 四、v20 决策引擎规则需求（需求级固化，全部纳入 P0）

> 本节为引擎输出内容的需求规格。**判定规则以 Python v20 引擎为唯一实现基准**，系统展示必须与引擎输出一致；本节用于验收核对（§7 验收标准 3、4）。

### 4.1 双维度分析（铁律一）

| 决策类型 | 使用维度 | 需求说明 |
|---------|---------|---------|
| 加价/降价/暂停 | **投放词（Targeting）** | 控制的是投放词竞价；搜索词聚合会混入其他投放词的广泛匹配流量 |
| 否定关键词 | **客户搜索词** | 否定的是实际搜索词 |
| 新建精准 | **客户搜索词** | 把广泛/短语下出单的搜索词提炼成精准投放 |

解析时**同时**做两套聚合（按投放列、按客户搜索词列），两套结果分别供上表三类决策使用，**禁止合并或互相冒充**。

### 4.2 词根族双层结构（铁律二、八.1）

- **L1 语义族**：品类词根 × 诉求词根。品类词根：胸部(breast/boob/bust/chest/senos)、臀部(butt/booty/glute/nalga/hip)、瘦身(fat/slim/belly/tummy/panza/grasa/sweat/cellulite)、护发(batana/bantana/botana/hair)、身体其他(body/skin)；诉求词根：增长·风险(enlarg/growth/bigger/plump/crecer/pills)、紧致提升(firm/lift/tighten/sag/perky/toning)、丰盈·合规(enhance/enhancer/boost)、燃脂(burn/melt/reduc/loss)。
- **L2 完全重复**：normalize（词序/单复数/同义词根）后完全一致 → 指向主词，**只有「关闭」一个处置，禁止独立调价**（铁律三·补）。
- **同词多匹配**：一个投放词开多层 → 保留 EXACT + 至多 1 探索层。
- **族级处置优先级**（自高向低）：风险族整族关 > 自动定向族关 > 0单且达止损线关 > 0单且族CTR<基准一半关 > ACoS≤40% 加投 > 40-60% 收缩 > >60% 重度收缩只留主词。
- 族级/活动级关闭**同样必须过双标准**（§4.3），未达标不可整族关。

### 4.3 双标准（关闭/否定唯一数据判据，铁律八.2）

```
可关闭+否定  ⟺  0单 且 ( 点击 ≥ 否定阈值  或  花费 ≥ 成本容忍值 )
两者都不满足 → 数据不足，不可判死刑：
    花费 ≥ $10  → 降竞价 30% 观察（不硬否）
    花费 <  $10  → 完全不动
```

| 阈值 | 算法 | 需求约束 |
|------|------|---------|
| 否定阈值（主用） | 既有出单词「点击/单」**中位数 × 2** | **每轮动态计算，禁止硬编码**（v19 实算 34 点击） |
| 统计检验（参考） | `ceil(ln0.05 / ln(1-CVR))` | 展示为参考值 |
| 成本容忍值 | **1.5 × 客单价** | 动态计算（v19 实算 $23.76） |
| 单单成本上限 | 客单价 × 毛利率 | CPA 超此即亏 |

**CTR 不是转化判据**：CTR 只能用于 ①CTR=0 且展示≥100 → 判「词不相关或 listing 无吸引力」，**可关但不否定**；②未达双标准但花费≥$10 时，CTR 低者降幅更大。**禁止用「CTR 低于基准」直接判关闭**（v18 曾误关 60 词）。

### 4.4 关闭 vs 否定（铁律八.2，不可混用）

| 处置 | 允许的依据（仅此几种） |
|------|----------------------|
| **关闭**（仅停投放） | ①合规风险 ②双标准达标 ③L2 完全重复（独立依据，与主词同批流量）④同词多匹配的 0 单探索层（结构去重）⑤CTR=0 且展示≥100（相关性差） |
| **否定**（阻断匹配，更严厉） | **只有两种**：①合规风险词 ②双标准达标（转化数据充分） |

L2 重复词 / 0 单探索层**只关不否定**（否定会误伤主词）；CTR=0 的词**只关不否定**（无转化数据，无权判定）。

### 4.5 合规风险词（红线，不看数据）

- 判定：同时命中 [胸/臀类目词根] × [增长宣称 enlarg/growth/bigger/grow/crecer/plumper]，或西语风险词（crecer los senos）。反例：`batana natural hair growth oil`（护发油）**不是**风险词。
- 处置：**一律暂停 + 否定**（账号安全优先）；输出批量表两行：关闭该词 + 活动级否定。中英文混杂词（丰胸等）与竞品词（kikookikoo/palmers）单独处理。

### 4.6 僵尸词与活动级 CTR 体检（铁律七）

- **僵尸词**：ENABLED 且展示>0 但 0 点击。处置：展示≥50 关闭，<50 留观（CTR=0 是 listing 主图/价格/标题问题，加减竞价无效）。
- **活动级 CTR 体检**：以主力线 CTR 为基准，< 主力线一半即判 listing 不合格 → 结论「广告降到最低维持，先修 listing 主图，CTR 回基准再放量」，**不是调竞价**。
- 只有 Targeting 报告能做以上两项（搜索词报告无展示量全景、无 0 点击词）。

### 4.7 分层架构与调价后层级复核（铁律五）

1. **bid 系数**：EXACT 1.00 / PHRASE 0.75 / BROAD 0.50；同族多层并存必须满足 **EXACT bid > PHRASE bid > BROAD bid**，任何情况下不允许倒挂。
2. **探索层硬约束**：拓词新增 BROAD 探索组 bid 上限 = 该族 EXACT 主词 bid × 0.5；探索层 final ≤ 上一层 final − 0.01；单轮降幅 ≤ 40%；不低于最低价 **$0.20**。
3. **BROAD 出单好于 EXACT 时禁止给 BROAD 提价**：正确动作 = 把 BROAD 捕获的出单搜索词提炼为独立 EXACT 新建（bid = 主词 final × 0.85，与主词重叠则并入主词），订单转移到精准层后逐轮把 BROAD 压向 EXACT×50%（收割逻辑）。
4. **调价后层级复核（强制）**：所有建议 bid 生成后，按词根族重跑 EXACT>PHRASE>BROAD 校验，**倒挂数为 0**；倒挂的用「上层锁定」约束重算（v19 教训：逐词按 ACoS 调价制造 breast firming lifting cream 倒挂）。
5. **探索层系数体检**：保留的多层词根实际 bid 系数（探索层 bid ÷ EXACT bid）逐族列明，与规范 0.75/0.50 对比；偏高（v20 实测 7 个 BROAD 系数 75~92%）处置：能关的层关闭，保留层先保证层级正确、逐轮向规范系数收敛（每轮降幅≤40%）；**绝不通过给探索层降价让 EXACT 显得合理**。
6. **短语层零转化判定必须用 Targeting 报告**（v17 证伪：搜索词报告漏单导致误判两层结构）。
7. 无 bid 数据时：输出「需用户从后台核对 bid」清单，**禁止用 CPC 推断层级**。

### 4.8 逐族拓词（铁律四、八.3）

- **每个 L1 族必须落一条拓词结论**，无遗漏：
  - 族≥3单且无 BROAD → ★开 BROAD（bid=主词×0.5）播**带修饰词的变体词**（for women / natural / firming / volume…，不是重复主词本身）；
  - 族≥3单且 BROAD 已出单 → ★收割（提炼精准，与主词重叠则并入）；
  - 族≥3单但 BROAD 0单 → 换变体策略；
  - 族2单 → 小预算试探（$3-5/天）；
  - 族1单 → 样本不足，先跑到 3 单；
  - 族0单但有增量点击 → 先治主词/修 listing，不拓；
  - 风险族/自动定向 → 不拓直接关。
- **增量判断**：搜索词出单>0 或 点击≥5，且来源不含本族 EXACT → 增量候选；来源含本族 EXACT → 主词已覆盖，不拓（提炼会重叠）。族级结论：主词出单≥3 且增量点击≥5 → ★值得拓。
- 增量搜索词按「当前由谁捕获」归族，避免两个族重复建议拓同一批词；族间联动：某族 BROAD 暂停后其长尾流量释放 → 由主词健康的族开 BROAD 接住。
- **ASIN 定向捕获的商品搜索词不构成关键词拓词空间，不提炼**。
- **必查「重复捕获」**：同一增量搜索词被 2+ 投放同时捕获且 0 单 = 互抢抬价 → 否定该词或关掉一路（v18 实例：butt firming and lifting cream 22 点击 0 单双捕获）。

### 4.9 引擎输出自检清单（交付前强制，全部必须通过）

1. L1 族总表：每族都有处置结论；
2. L2 完全重复清单：每条含「保留主词/关闭变体」，重复词无独立调价建议；
3. 同词多匹配处置不自相矛盾（判定顺序：L2重复 → 有无EXACT层 → EXACT是否出单 → 关0单探索层）；
4. 关闭矩阵：全量组合逐条，每条带 CTR + CPA + 依据文字；
5. 拓词评估：每族一行结论 + 增量搜索词明细（含「当前由谁捕获」）；
6. 关闭预演：关闭 X% 花费后 ACoS 变化，明确说明「是否还需叠加调价/修 listing」；
7. 正文数字与表格一致；
8. 调价后层级复核倒挂数为 0；
9. 探索层系数体检表已列明并与规范对比；
10. 凡 BROAD/PHRASE 出单好于 EXACT 的族，已给「提炼新精准」而非给探索层提价；
11. 批量表改价行含层级约束后的数值，非纯按 ACoS 的数值。

## 六、业务流程

### 6.1 正常流程（Happy Path）

```
[上传] 站点管理已绑定账户 → 投流优化中心选账户+日期 → 上传双报告（搜索词 xlsx + Targeting csv）
  → 解析校验（列名探测/数值清洗/口径一致性警告）→ 落 AdReport（原始数据+文件归档）
[分析] 点击「开始分析」→ 后端调用 v20 引擎（子进程+JSON 交换，120s 超时，失败重试 1 次）
  → 引擎输出校验 → 落 AdRecommendation + AdKeyword 决策字段 → 返回 recommendationId
[查看] 前端展示：账户总览 → 族级总览（Tabs+徽章）→ 关闭矩阵/否定清单/拓词/层级核对（分页表）
  → 执行摘要条（关闭 X% 花费 → ACoS 预演）
[勾选] 用户逐条核对依据文字 → 勾选/取消 → 必要时手工覆写（改动作/改 bid 值，标注手工修改）
[生成] 点击「生成批量操作表」→ 服务端自检（4 项全 0）→ exceljs 生成 33 列 xlsx + 使用说明 txt
[执行] 用户下载 → 后台「批量操作」先下载现有表格备份 → 核对列名 → 上传批量表 → 后台执行
  → 下载「处理结果」核对成功行数 → 回滚预案（备份表原样上传）
[沉淀] 报告/决策自动入历史 → 下期报告上传后可与本期决策对比复盘
```

**状态流转**：报告 `UPLOADED → ANALYZING → ANALYZED`；分析失败 `→ ANALYZE_FAILED`（可重试）；批量表每次生成记录操作日志。

### 6.2 异常流程

| 编号 | 异常 | 处理 | 用户可见反馈 |
|------|------|------|-------------|
| E1 | **报告格式错误**（文件损坏/列名探测失败/必填列缺失/行数=0） | 解析器给出具体失败点（缺哪列/哪个文件），**不落库** | Toast + 错误详情（含列名风险提示：不同站点模板列名可能不同） |
| E2 | **引擎失败**（exit code 非 0 / 输出 {ok:false} / 超时） | 自动重试 1 次；记录 stderr 全量日志；报告状态置 ANALYZE_FAILED | 错误信息 + 「重试」按钮；原始文件保留可重新分析 |
| E3 | **无投放报告**（只传了搜索词报告） | 系统允许上传但**禁止产出 bid 调整/层级核对结论**；输出 ⚠️ 提示 + bid/状态待核对清单（用户可从后台补，或等 API） | 页面上方警示条，明确哪些区块不可用及原因 |
| E4 | **口径不一致**（双报告偏差 >15%） | 阻断分析，要求确认日期窗口/账户一致后重传 | 警告弹窗列出两报告花费/订单差异 |
| E5 | **批量表自检失败**（4 项任一非 0） | 拒绝生成，返回具体缺 ID 的行 | 错误详情 + 提示重新勾选或联系管理员 |
| E6 | **无勾选动作** | 点击生成时提示 | 确认弹窗「执行清单为空，确认生成空表？」 |
| E7 | **引擎版本不兼容**（services/amazon-ads-engine 与 v20 契约不符） | 输出 JSON 校验失败即按 E2 处理；版本号记录在 AdRecommendation.version | 错误提示 |
| E8 | **重复分析**（同一报告二次分析） | 允许，生成新版本，旧版本保留 | 历史列表显示多个版本 |
| E9 | **上传超大文件**（>50MB） | 拒绝并提示（报告实际 <10MB，限制防滥用） | 错误提示 |

## 七、验收标准

> 「做完」的可操作定义。全部通过才算 M1 验收完成。

### 7.1 功能验收

1. **AC-1 引擎一致性（核心验收）**：用 `~/clawd/amazon-ads-optimizer` 真实 v20 报告（Ads Amazon 文件夹的搜索词报告 + Targeting 报告）上传分析，系统输出（经 `services/amazon-ads-engine/analyze_cli.py` 适配层）的 `account/families/closeMatrix/negateList/expandTable/layerCheck/summary` 与 Python CLI 直接运行结果**逐字段一致**（数字误差为 0，JSON 结构一致）。**对比基准 CLI = `services/amazon-ads-engine/analyze_cli.py`（与 amazon-ads-optimizer 的 `main.py analyze` 输出同源）**。
2. **AC-2 双维度正确性**：对已知 3 处历史误判案例（enhance breast cream、bigger breast、breast firming）用真实报告回归，系统结论必须与 v20 修正后结论一致（投放词维度 ACoS 判断，不出现「搜索词聚合误判加价」）。
3. **AC-3 层级复核**：任意真实报告跑批后，调价后层级复核倒挂数 = 0；探索层系数体检表逐族可展开核对。
4. **AC-4 双标准动态计算**：否定阈值/成本容忍值按报告数据动态算出（= 中位数×2 / 1.5×客单价），代码中无硬编码阈值（审查确认）。
5. **AC-5 批量表自检**：真实报告生成批量表，4 项自检全为 0；ID 三件套齐全率 100%（对标 v18.1 实测 127/127）；改价行 Bid 值为层级约束后的值。
6. **AC-6 全流程走通**：上传 → 分析 → 查看（5 个展示区全渲染）→ 勾选 → 生成下载 → 文件可用 exceljs/Excel 打开校验列头与行内容，全链路 1 次成功。
7. **AC-7 权限边界**：viewer 访问广告 API 返回 403 且页面不可见数据；sales 无法访问站点管理写接口；凭据字段任何角色读取均为脱敏值。
8. **AC-8 站点管理**：创建 US 账户 → 上传分析 → 列表按账户隔离；多账户数据互不串。
9. **AC-9 异常路径**：E1~E9 逐一演练，均有正确反馈且不产生脏数据（失败不落库/落失败状态）。
10. **AC-10 可追溯性**：任取一条建议（如某词关闭），点击可看到：依据文字 + 对应的原始报告行（点击/花费/CTR/CPA/搜索词来源）+ 所属 L1 族。

### 7.2 验收方法

| 项 | 方法 |
|----|------|
| AC-1~4 | 用真实 v20 报告做回归比对（Python CLI vs 系统输出，脚本化 diff） |
| AC-5 | 生成批量表后用 openpyxl/exceljs 读回校验（不只看「生成成功」） |
| AC-6 | 浏览器实测（dev 端口 3001）全流程 |
| AC-7 | 三种角色账号逐接口 curl + 前端实测 |
| AC-9 | 构造坏文件/坏报告/单报告/超时场景逐项演练 |

## 八、隐性需求

> 用户是老板，会**逐条核对数据**。以下为必须满足的隐性要求（不满足即返工）。

1. **R1 全量可追溯**：任何「这个词出单/该关/该加价」的结论，都要能回答「是哪个投放词的哪一行带来的」。每条建议动作（AdKeyword.actionReason）必须包含：判定依据类型（双标准/合规/重复/层级约束/僵尸词…）+ 关键数字（点击/花费/ACoS 或阈值对比）。点击结论可展开到 AdReport.rawRows 对应原始行。
2. **R2 所有建议有依据文字**：关闭矩阵每条、否定清单每条、拓词结论每族、层级复核每条警告，都必须带人类可读的依据文字，禁止只给动作不给理由。
3. **R3 批量表列名需用户模板核对**：交付前必须提示用户先从后台「批量操作」下载现有表格 → (a) 作回滚备份 (b) 核对列名（中文列名或列序不同则按用户模板重排后再交付）。此流程写入使用说明 txt，并在 UI 下载按钮旁提示。
4. **R4 数字一致性**：同一页面的所有数字同源（读同一 Json 快照），禁止前端二次聚合/换算导致与引擎输出不一致。
5. **R5 结论可被挑战**：用户质疑时系统能按「双维度 → Targeting 口径 → 原始行」逐层下钻自证；不提供「权威语气但无法核对」的结论。
6. **R6 状态可见**：投放词状态（ENABLED/PAUSED）从 Targeting 报告自动读取并在矩阵中展示（v8 教训：忽略状态导致给了「维持暂停词」错误建议）。
7. **R7 变更留痕**：手工覆写、批量表生成、报告删除等操作记录操作日志（谁、何时、改了什么）。
8. **R8 引擎升级不破坏**：引擎规则更新（v20→v21）时历史决策快照仍可读、可对比；新版本跑批不覆盖旧版。

## 九、非功能性需求

### 9.1 性能

| 项 | 指标 |
|----|------|
| 报告解析+落库 | ≤ 10s（双报告合计，真实报告 <5MB 场景） |
| 引擎跑批（分析） | ≤ 120s 超时；常规 ≤ 30s；超时自动重试 1 次 |
| 结果页首屏 | ≤ 3s（P0 接口 + 骨架屏） |
| 批量表生成 | ≤ 10s（200 行内） |
| 并发 | 支持 2 个分析任务并行（引擎子进程隔离），超出排队 |
| 上传限制 | 单文件 ≤ 50MB；支持类型 xlsx/csv |

### 9.2 安全

| 项 | 要求 |
|----|------|
| 凭据加密 | AdAccount 的 clientId/clientSecret/refreshToken 用现有 `src/lib/crypto-utils.ts`（AES）加密存储；**禁止明文落库**；接口返回脱敏（后 4 位） |
| 权限 | 所有 ads API 按权限点校验（见 §5）；viewer 默认无 ads:view |
| 审计 | 批量表生成、覆写、账户变更记日志（含操作人） |
| 文件安全 | 上传文件存服务器私有目录（非 public），下载走鉴权接口 |
| 注入防护 | 引擎子进程参数白名单化（文件路径来自系统生成，不拼接用户输入）；遵循现有 CSRF/中间件约定 |
| 数据保留 | 原始报告文件与决策快照只增不删（除非 admin 显式删除） |

### 9.3 可维护性

- **数据获取层抽象**：业务层不感知 Manual/Api 来源，M2 切换零改动（§3.2 REQ-ADS-007）。
- **引擎契约化**：analyze_cli.py 输入输出 JSON 契约固定 + 版本字段；契约校验失败按 E2 处理，便于引擎独立升级。
- **代码组织**：引擎服务（`services/amazon-ads-engine/`）与 ERP 应用代码分离，引擎升级只动服务目录。
- **可观测**：引擎调用日志（入参文件/耗时/exit code/stderr）全量留存，用于问题定位。
- **UI 一致性**：遵循现有组件约定（CSS 变量/骨架屏/Toast/分页/fade-in），移动端 table-auto+nowrap+truncate。

### 9.4 兼容性

- 报告解析兼容新旧列名（旧投放报告 vs 新版 Targeting CSV，见 REQ-ADS-001-3）。
- 决策引擎 JSON 结构向后兼容（新增字段不破坏旧快照读取）。

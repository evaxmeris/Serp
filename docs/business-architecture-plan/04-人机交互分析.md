## 0. 探查结论速览（先给判断）

| # | 判断 | 关键证据 | 影响 |
|---|---|---|---|
| 1 | 系统是**"功能菜单的集合"，不是"角色工作台"** | 侧栏 9 组 40 项全量平铺（`Sidebar.tsx:73-437`），无角标、无待办；首页只做 KPI 展示（`dashboard/page.tsx:284-460`） | 用户每次登录都要自己"找活干"，认知成本高 |

## 1. 角色工作台设计

### 1.1 现状：有"指标过滤"，没有"工作台"

```
现有 dashboard/page.tsx 的真实结构
┌──────────────────────────────────────────────┐
│ 📊 经营看板            [近7天 ▾]              │  ← 时间筛选，与角色无关
├──────────────────────────────────────────────┤
│ [待办订单][库存预警][审批待办][待收款][今日销售额] │  ← 5 卡塞 4 列(135 行 slice(0,5))
├──────────────────────────────────────────────┤
│ 销售额折线          │ 渠道饼图                │  ← API 路径下恒为空数组(203-206)
├──────────────────────────────────────────────┤
│ ⚡ 快捷操作（按角色过滤 8 个按钮）             │
├──────────────────────────────────────────────┤
│ 最近待办订单        │ 最近审批                │  ← mock 数据；卡片不可点击
└──────────────────────────────────────────────┘
```

**四个结构性问题：**

1. **不可点击**：`Card` 只是 `div`（`dashboard/page.tsx:287`），指标卡看到"库存预警 5 款"却点不进去，用户必须自己回忆去哪个菜单。
2. **数据不可信**：API 失败静默回退到**硬编码 mock**（`:179-185`，`:210`，`:213`），页面显示"待办订单 18 / 毛利率 43.25%"，用户无从分辨真假。
3. **语义错绑**：`monthlyGrossMargin: apiData.sales?.growth`（`:201`）——把"增长百分比"当"毛利率"显示，属数据事故级 bug。
4. **指标卡对角色是"砍"而不是"配"**：`getMetricCards` 只按 `roles` 过滤后 `slice(0,5)`，仓储看到"待办订单/库存预警"两张就没别的了——**仓储真正需要的是"待出库单 N 张、今日应发 M 单"**。

### 1.2 角色模型改造（前置条件）

| 业务角色 | 现有映射 | 应新增角色值 | 权限码基线（沿用现有 permission 命名） |
|---|---|---|---|
| 老板 | `admin` | `owner`（只读全域 + 财务可见） | `dashboard:view` `report:view` `finance:list` `order:list` `inventory:list` `approval:list`（只读） |
| 销售 | `sales` ✓ | — | `inquiry:*` `quotation:list` `order:list` `customer:list` `product:list` `invoice:list` |
| 采购 | `purchasing` ✓ | — | `supplier:list` `purchase:list` `inbound_order:list` `logistics_order:list` `inventory:list` |
| 仓储 | `warehouse` ✓ | — | `inbound_order:list` `outbound_order:list` `inventory:list` `shipment:list` `quality:*` |
| 运营 | `sales`（`ads:view`） | `ops` | `ads:view` `ads:admin` `platform:list` `sync:view` `replenish:view` `overseas_inventory:view` |
| 财务 | `admin`（`finance:list`） | `finance` | `finance:list` `invoice:list` `payment:*` `reimbursement:*` `logistics_finance:confirm` |

**必须同时修的三个实现点：**

- `getCurrentUserRole()` 拿不到 localStorage 时**默认返回 `'admin'`**（`Sidebar.tsx:743-753`）。这不是"兜底"，这是"降级成最大权限视图"。应改为返回 `null` 并让工作台进入"未识别角色"态（只显示通用待办），同时在 `getCurrentUserContext`（`:759-785`）失败时记审计日志。
- 新增角色后，`filterMenu`（`:448-465`）的权限优先逻辑可直接复用，无需改结构——**IA 改造与权限体系解耦，这是现有代码的加分项**。
- 工作台卡片的 `roles: UserRole[]` 数组（`dashboard/page.tsx:41`）应升级为 `permission?: string`，与侧栏同一套判据，避免"角色白名单 + 权限码"两套逻辑并存。

### 1.3 工作台设计原则

> **首屏回答一个问题：「我，此刻，必须处理什么？」**

五层骨架（自上而下，每层都可折叠，默认只展开前两层）：

```
L1  身份条     早上好，王芳 · 仓储主管 · 上海仓        [角色切换预览(admin)]
L2  待办队列   红/橙/黄三级；每张卡=一个可执行动作，带数量+最老时效+SLA 超时
L3  风险预警   库存低于安全线 / 同步陈旧 / 差异待核 / 单据卡单
L4  我的进度   三条业务链的漏斗或管道视图（B2B / 备货 / 平台）
L5  趋势分析   金额趋势、渠道占比、毛利（老板/运营默认展开，其余折叠）
```

**L2 待办卡片的组件契约（统一一个 `<TodoCard>`，禁止各页自造）：**

```ts
interface TodoCard {
  key: string;                 // 'outbound.pending'
  title: string;               // '待出库'
  count: number;               // 主数字，0 时整卡降为灰态不隐藏（避免"今天没事"的错觉）
  unit?: string;               // '张' / '款' / '单'
  oldestAgeHours: number;      // 最老一条的滞留时长 → 决定颜色
  slaHours: number;            // 该动作的时效标准，超出即红
  severity: 'normal' | 'warn' | 'critical';
  href: string;                // 必带筛选参数，如 /outbound-orders?status=PENDING&sort=createdAt.asc
  cta: string;                 // '去发货'
  hint?: string;               // '其中 3 张已滞留 >48h'
}
```

交互规则：
- **整卡可点**，hover 抬升 1px + 边框变主色（沿用 `fade-in` 过渡），键盘 `Tab` 可达、`Enter` 进入。
- **数字为 0**：卡片灰阶显示"暂无待办 ✓"，不做移除——移除会让用户怀疑"是不是没加载出来"。
- **超过 SLA**：卡片左侧 3px 红条 + 数字前加 ⚠ 图标 + `aria-label="已超时 12 小时"`。
- **右下角"批量"**：卡片 hover 时浮出次要动作（如"批量发货"），直接跳列表页并预勾选。
- **不刷新整页**：卡片数据 60s 轮询（`/api/v1/workbench/summary`），切回标签页时强制刷新（`visibilitychange`）。

**统一数据契约（新增，聚合现有表，不新增业务表）：**

```
GET /api/v1/workbench/summary?role=sales
{
  generatedAt, role,
  todos: [TodoCard...],           // 按 severity → count 排序
  risks: [{ key, level, title, count, href }...],
  pipelines: {                    // L4 漏斗
    b2b:   { inquiries: 12, quotations: 8, orders: 5, pendingOutbound: 3 },
    stock: { purchasePending: 4, inTransit: 2, inboundPending: 3, overseasLow: 7 },
    platform: { accounts: 6, syncedToday: 4, stale: 2, orderDiff: 11 }
  }
}
```

### 1.4 六角色首屏（明确到"看到什么、点哪里"）

#### ① 老板 / owner（决策视角，只读）

| 区块 | 内容 | 数据源 | 交互 |
|---|---|---|---|
| 今日经营条 | 今日销售额 · 本月毛利额/率 · 回款率 · 在手订单额 | `sales.totalRevenue`、`ProfitDetail`、`Invoice.balanceDue` | 点数字 → 对应报表页并带 `?period=today` |
| 卡单红榜 | 「滞留 >3 天」的单据聚合：未出库订单 / 待财务确认物流单 / 待校对 >24h | `Order.status`、`LogisticsOrder.approvalStep` + `submittedAt` | 点击进"审批中心-超时"标签页 |
| 资金侧 | 待收款 Top5 客户、应付物流费待签收金额 | `Invoice`、`LogisticsOrder` PENDING_FINANCE | 展开行内明细，不跳页 |

#### ② 销售 / sales（阿里国际站履约）

| 待办卡 | 触发条件 | 点进去 |
|---|---|---|

### 1.5 角色工作台与现有页面的关系

- **`/dashboard` 保留为"经营看板"**（老板/运营主用，图表 + 趋势），
- **新增 `/workbench` 作为所有角色的登录落地页**（`/` 与登录成功后重定向到此处），

### 2.1 现状盘点（9 组 40 项，问题逐条可查）

**侧栏不可达页面（8 个，实测）：** `/inquiries`、`/approvals`、`/purchases`、`/users`、`/product-research`、`/profile`、`/pending-approval`、`/.`。
**另有 28 处页面级原生 `<select>`、19 处手写分页**，与 shadcn 风格不一致（详见第 4 章）。

### 2.2 目标 IA：按"业务链"组织，而不是按"实体表"组织

核心判断：**用户的心智是"一条单子怎么走完"，不是"系统里有哪些表"。** 因此一级导航 = 业务链，二级 = 链上节点（严格平级，不出现三级菜单）。

```
① 工作台        ← 新增，登录落地页（角色化待办）
② B2B 销售      询盘 → 报价 → 客户 → 订单 → 出库
③ 备货与履约    采购 → 物流订单 → 入库 → 海外仓库存
④ 平台经营      平台订单 · 库存镜像 · 补货建议 · 广告 · 同步状态
⑤ 审批中心      ← 新增，所有需要"我签字"的单据（含物流四级）
⑥ 财务          发票 · 应收 · 应付 · 收付款 · 报销

**① 关联选择器：用 `Sheet`（右侧 960px 抽屉）而不是下拉**

```
┌─ Sheet：选择要出库的销售订单 ────────────────────────────────┐
│ 🔍 [输入订单号/客户/SKU，实时搜索]     仓库: [上海仓 ▾]       │

│ ☑ | SO-2310-0021 | ABC Co. | 10-25 ⚠2d | 300     | 已确认  │

**② 明细表：从"全量硬填"改为"勾选 + 可编辑"**

| 列 | 交互规格 |

| ☑ 行选择 | 默认全选；取消勾选=本次不出该 SKU（比现状"填 0"更符合语义，且不会误建 0 数量行） |

### 3.b 海外仓库存页 —— 双视角 + 镜像/台账对照

#### 现状

- 已有 `OverseasWarehouse`（含 `fbaSyncEnabled`、`lastSyncAt`、`apiEnabled`）与 `OverseasInventory`（`availableQty / inboundQty / reservedQty / totalQty / lastFulfillableQty / costPerUnit / lastSyncAt / updatedAtSource`）**完整模型，`src/` 中 0 引用**。

#### 设计：一页两视角、一表两来源

```
┌ 海外仓库存 ─────────────────────────────────────────────────────────┐
│ [按仓库 (4)] [按 SKU (128)]        🔍[SKU/ASIN/FNSKU]  平台[全部▾]  │  ← 视角 Tabs+计数；筛选右对齐

├────────────────────────────────────────────────────────────────────┤
│ 按仓库视角                                                          │
│ ┌ 美国仓 FBA (US) ── ● 已同步 2min ── 可售 8,420 ── 低库存 5 款 ──┐ │  ← 仓库卡片网格
│ │  [进入该仓明细 →]                                              │ │
│ └────────────────────────────────────────────────────────────────┘ │
│ 进入后：SKU × 指标表（如下）                                        │
└────────────────────────────────────────────────────────────────────┘
```

**核心表（两视角共用同一张，列按视角增减）：**

| SKU | 品名 | 仓 | 平台可售 | 平台在途 | 预留 | **本地台账** | **差异** | 更新于 |
|---|---|---|---|---|---|---|---|---|
| A-001 | 夜光笔 | US-FBA | 120 | 300 | 8 | 118 | **-2** | 2min |
| A-014 | 圣诞帽 | US-FBA | 0 | 0 | 0 | 46 | **+46** 🔴 | 2min |
| B-007 | 手环 | UK-FBA | 210 | 0 | 5 | 210 | 0 ✓ | 6h |

**差异高亮规则（必须显式定义，否则"高亮"等于没高亮）：**

| 差异绝对值 | 视觉 | 语义 |
|---|---|---|
| 0 | 灰 `0 ✓` | 一致 |
| 1 ~ 阈值(默认2，可按 SKU 配) | 无底色，数字加粗 | 可容忍（在途/退货抖动） |
| > 阈值 | 琥珀底 `+46`，行左 3px 琥珀条 | 需核对，行尾出现「核对」按钮 |
| > 10 或 平台可售=0 且本地>0 | 红底 + ⚠ 图标 + `aria-label="差异 46 件，疑似未同步"` | 高危：可能已断货或超卖 |

**"平台镜像 vs 本地台账"的呈现原则：**

1. **绝不二选一 hiding**：两列并排永远同时出现，差异列是第三列派生值——用户自己判断以谁为准。
2. **来源可辨**：表头加小图标，平台列 `Amazon 图标`，本地列 `仓库图标`；鼠标悬停显示来源时间戳（`lastSyncAt` / `updatedAtSource`）。
3. **以谁为准要用户显式选**（不自动覆盖）：行内「核对」→ 抽屉：

```
┌ 差异核对 — A-014 圣诞帽 (US-FBA) ────────────────────┐
│ 平台可售 0 · 本地台账 46 · 差异 +46                  │
│ 时间线：本地最后变动 10-20 14:22（出库单 SH-0231）   │
│         平台最后同步 10-23 09:10                     │
│ 可能原因：平台侧已售罄/移仓，或本地出库未回写         │
│ [以平台为准(生成 -46 调整)] [以本地为准(推送平台)]   │
│ [标记忽略(7 天内不再提示)]  备注:[____________]       │
│ 影响：以平台为准将锁定 46 件为不可售，需主管审批 →    │
└──────────────────────────────────────────────────────┘
```
4. **批量核对**：勾选多行 → 底部 `BatchActions`（已有组件，0 引用）：「批量以平台为准」「导出差异清单」。
5. **陈旧度前置**：整页顶部固定"数据截至"条。`lastSyncAt` > 24h 琥珀、> 72h 红，且**在表内该行"更新于"列同步变色**——避免用户拿 3 天前的镜像做补货决策。

**按 SKU 视角额外能力：** 一个 SKU 展开成"各仓一行"（US/UK/DE 可售合计），并显示 `周转天数 = 可用 / 近30日均销`、`预计断货日`。这为 3.c 的补货建议提供入口：「生成补货建议」按钮直接带 `sku` 参数跳转。

**空态与加载：**
- 未配置任何海外仓 → `EmptyState`：「还没有海外仓 —— 去基础数据 › 仓库配置添加」（不让用户对着空白页猜）。
- 同步中 → 表格 `Skeleton` 行 + 顶部条显示"正在同步美国仓…"，**不 disable 整个页面**（用户仍可看上次数据，标注"上次数据"）。

#### 页面三段式：参数 → 建议表 → 转换

```
┌ 补货建议 ────────────────────────────────────────────────────────────┐
│ 覆盖天数[45] 安全库存[30天] 起订量取整☑ 含在途☑    [重新计算建议]     │  ← 参数面板（默认折叠为一行）
│ 上次计算 10-23 08:00 · 覆盖 128 SKU · 建议 23 项 · 预计占用 ¥86,400    │
├──────────────────────────────────────────────────────────────────────┤
│ [需处理 (18)] [已转采购 (4)] [已忽略 (1)]              🔍 SKU  平台[▾] │  ← Tabs + 计数
│ ☑ | SKU  | 平台可售 | 在途 | 日均销量 | 覆盖天数 | **建议量** | 紧急度 | 预计断货 | 动作      │
│ ☑ | A-001| 120     | 300  | 8.2     | 14       | **270**   | 🔴 紧急 | 11-02   | [转采购/转物流]│
│ ☐ | B-007| 210     | 0    | 3.1     | 68       | **90**    | 🟡 关注 | 01-15   | …            │
│ ─────────────────────────────────────────────────────────────────────│
│ 已选 3 项 · 建议总量 620 · 预估金额 ¥42,800                            │
│                        [批量转采购单] [批量转头程物流单] [导出]        │  ← 吸底操作条
└──────────────────────────────────────────────────────────────────────┘
```

**建议量算法（可解释，必须展示推导过程）：**

```
建议量 = ⌈(日均销量 × 覆盖天数 + 安全库存 - 平台可售 - 在途) / MOQ⌉ × MOQ，下限 0
```
行内点击「建议量」弹出气泡，逐项列出公式代入值——**补货建议最怕"黑盒数字"，可解释性是采纳率的关键**。
紧急度：`预计断货日 - 今天 ≤ 头程时效(默认 35 天)` → 红；`≤ 60 天` → 黄。**头程时效必须参与紧急度计算**，否则"3 月才断货"的建议会被当成紧急件空运。

**转换交互（本页最关键的一步）：**

```
点「批量转采购单」
  ↓
① 分组预览抽屉（不是直接提交）
   按供应商分组：供应商A（2 SKU，620 件）/ 供应商B（1 SKU，90 件）
   显示：单价来源（最近采购价）、交期、合计金额、将生成的采购单号预览
   每行可改：供应商（下拉）、采购数量（默认建议量，改后合计实时更新）
  ↓
② 二次确认（明确的副作用陈述）
   「将创建 2 张采购订单（草稿状态），不会自动提交审批」
   [取消] [创建 2 张草稿单]
  ↓
③ 结果反馈（不吞错）
   成功 2 / 失败 0 → toast.success + 建议状态改为「已转采购」并附采购单链接
   部分失败 → 抽屉内保留失败行 + 每行失败原因 + 「重试失败项」
```

**转物流单（头程）** 同理，但确认项不同：「目的仓、运输方式（海运/空运）、预计发运日、是否合并同仓其它建议」，并明确提示"头程物流单仍需走四级审批"——**这条提示很关键**，否则用户以为转单即发运。

**状态机（写进契约，避免"建议表越用越脏"）：**

```
SUGGESTED ──转采购/转物流──> CONVERTED ──单量变更──> NEEDS_RECALC
    │                              │
    ├──忽略(需填写原因/7天有效期)──> DISMISSED ──到期──> SUGGESTED
    └──覆盖天数变化触发重算──> SUGGESTED(新版本, 旧版 archived)
```

**并发与幂等（必须显式设计）：**
- 建议行加 `version`；转换请求带 `Idempotency-Key`（建议 id + version），重复点击不产生第二张采购单。
- 同一 SKU 在同一供应商下已有 `DRAFT` 采购单 → 转换时提示"合并到 PO-2310-0031（数量 +270）"或"新建"，二选一由用户决定。

**空态：**
- 无建议：「当前库存均高于安全线 👍」+ 显示"下次计算时间"（而不是空白）。
- 无海外仓/无平台数据：「补货建议依赖平台库存与销量数据 —— 先去配置平台账号 →」。

### 3.d 平台同步状态页 —— 各站点同步时间 / 状态徽章

#### 现状

- 「数据同步」菜单项 → `/sync` → **`redirect('/orders')`**（`(dashboard)/sync/page.tsx:3-5`），点进去直接掉到订单页，用户以为系统出错。
- 数据层齐备：`PlatformSyncConfig`（`syncIntervalMin`、`lastSyncAt`、`lastSyncStatus`、`isSyncing`）、`PlatformSyncLog`（`ordersFound/Synced/Failed`、`durationMs`、`retryCount`、`errorMessage`）、`PlatformAccount`（`lastSyncAt`、`syncStatus`、`errorMessage`）。
- 现有 `/settings/platforms` 只显示账号是否启用（`platforms/page.tsx:143-157`），**不显示同步健康度**。

#### 设计：状态矩阵 + 可展开历史

```
┌ 平台同步状态 ────────────────────────────────────────────────────────┐
│ 整体: 6 站点 · 4 正常 · 1 延迟 · 1 失败        [全部立即同步] [设置]  │
├──────────────────────────────────────────────────────────────────────┤
│ 平台      店铺          状态       最近同步        本次同步    下次     │
│ Amazon   US-Main      ● 正常      2 分钟前        128 单 ✓    2h 后   │
│ Amazon   UK-Main      ● 延迟 ⚠    6 小时前        0 单        已过期  │
│ TikTok   Global       ● 同步中 ◌   进行中 3min…   —           等待中  │  ← 该行按钮禁用
│ Amazon   DE-Main      ● 失败 🔴    3 天前         错误 1 条   [重试]  │  ← 失败必带"重试"
│ Alibaba  阿里主店      ● 未配置 ○   —              —          [去配置]│
└──────────────────────────────────────────────────────────────────────┘
```

**徽章规范（四态 + 一灰）：**

| 徽章 | 颜色/图形 | 判定条件 | 附加文案 |
|---|---|---|---|
| 正常 | 绿点 + "正常" | `lastSyncStatus=success` 且 `now-lastSyncAt < 2×syncIntervalMin` | `2 分钟前` |
| 延迟 | 琥珀点 + "延迟" | `success` 但 `now-lastSyncAt > 2×interval` | `6 小时前`，行内显示"上次成功 09:00" |
| 同步中 | 蓝色旋转 + "同步中" | `isSyncing=true` | 按钮 disabled，progress 显示"已处理 3/12 页"（有则显示，无则显示耗时） |
| 失败 | 红点 + "失败" | `lastSyncStatus=failed` | 展开错误摘要 + `[重试]`（指数退避提示：下次自动重试 14:30） |
| 未配置 | 灰空心 + "未配置" | 无 `PlatformSyncConfig` 或无凭据 | `[去配置]` |

**交互细节（每一条都对应一类真实抱怨）：**

1. **相对时间 + 绝对时间双显**：`2 分钟前`（大字）+ 悬停/副行 `10-23 09:12:44`。运营判断"要不要手动同步"看的是相对时间，排查问题看绝对时间。
2. **"立即同步"防连点**：点击后按钮立即进入 3s 冷却（`disabled` + 倒计时"15s 后可再触发"），避免用户狂点造成平台限流被 ban。**这一条比 UI 好看重要得多**（`PlatformSyncConfig.isSyncing` 是互斥锁，但 UI 层连点仍会打多次请求）。
3. **失败可展开、可重试、可跳日志**：行展开显示 `errorMessage`（脱敏：不暴露 token）+ 最近 5 条 `PlatformSyncLog`（时间、触发方式、拉取/成功/失败数、耗时）；「查看全部」进抽屉。
4. **陈旧度预警前置**：页面顶部若存在 `> 72h` 站点，显示琥珀横条「英国仓数据已 3 天未更新，库存/补货建议可能失真 → [立即同步]」——把数据质量风险暴露在用户决策之前。
5. **同步日志抽屉**（`PlatformSyncLog` 直接可渲染）：

```
┌ 同步历史 — Amazon US-Main ─────────────────────────────┐
│ 触发     时间       状态    拉取  成功  失败  耗时      │
│ 定时     09:12     成功    128   128   0     4.2s      │
│ 手动     08:40    部分     120   117   3     6.8s  [看失败详单]│
│ 重试     08:52     成功    3     3     0     1.1s      │
└────────────────────────────────────────────────────────┘
```
6. **路径**：`/platform/sync`（替代 `/sync`），并在侧栏「平台经营」组内以角标显示"失败/陈旧站点数"。
7. **权限**：`sync:view` 可见，`sync:execute` 才能点"立即同步"（现状 `sync` 菜单仅 admin，运营看不到——运营才是最该看的人）。

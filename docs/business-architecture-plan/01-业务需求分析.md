## 1. 业务本质与总体判断

公司同时跑**两条商业模型完全不同的业务**，这是全部需求分析的出发点：

| 维度 | 阿里国际站（B2B 批发） | 亚马逊 4 站点 + TikTok Shop（平台零售） |
|---|---|---|
| 交易对手 | 企业买家（贸易商 / 品牌商 / 分销） | 终端消费者 |
| 订单来源 | 询盘 → 报价 → 谈判 → 成交 | 平台自动生成，ERP 不参与 |
| 履约主体 | **本公司**（备货、报关、发运） | **平台**（FBA / 平台仓发货） |
| 库存位置 | 国内仓（主）+ 可选海外仓 | 平台仓（FBA/平台仓），只读 |
| ERP 该做什么 | **主动管理全链路**：订单→出库→发运→收款 | **只读镜像 + 海外仓备货管理** |
| 结算 | 按合同/信用证/T/T，多币种 | 平台定期结算，扣佣金/仓储费 |
| 失败代价 | 发错货、超卖、账实不符 | 断货（断货=排名下滑，损失最大） |

**核心判断（需在立项时锁定）**：
1. B2B 是"单据驱动"，ERP 必须是**权威数据源（system of record）**。
2. 平台零售是"事件驱动"，ERP 只能是**镜像 + 决策支持**，绝不可反向干预平台履约。
3. 两者的交汇点只有三处：**产品主数据（SKU）**、**海外仓实物库存**、**资金/利润汇总**。系统设计必须围绕这三个交汇点做隔离，其余部分彻底解耦。

**当前系统最危险的结构性问题**（详见第 5 章）：
平台零售订单经 `order-sync.ts` 直接写入 B2B 的 `Order` 表并自动创建 `Customer`，使两类业务共用一张销售订单表。这会导致：B2B 订单列表被零售单污染、零售单被误纳入出库流程、客户主数据被 `AMAZON-Customer-xxx` 类垃圾记录灌满、销售业绩与毛利口径失真。**这是 P0 级架构缺陷，必须在功能扩展前修正。**

## 2. 利益相关者与角色

### 2.1 角色全景

系统现有 RBAC 结构：`User` / `Role` / `Permission` / `UserRole` / `RolePermission`（`schema.prisma` 1264–1325），另有 `UserRegistration` 注册审批。角色划分建议与诉求如下。

| 角色 | 系统内定位 | 核心诉求（他要什么） | 主要痛点（现在怎么难受） | 关键场景 |
|---|---|---|---|---|
| **老板 / 总经理** | 全局只读 + 审批终审 | 一眼看清：本月两条业务线各赚多少、钱压在哪、哪个 SKU 要断货、哪个客户欠款 | 平台佣金/仓储费与 B2B 毛利混算，看不到真实净利；海外仓有多少货靠问人 | 月度经营复盘、大额采购/物流审批、备货决策 |
| **销售（外贸业务员）** | 客户 + 询盘 + 报价 + 订单 Owner | 快速报价、跟单不漏、提成算得清 | 报价靠 Excel；订单变更不同步仓库；不知道能否按期交货 | 询盘转报价转订单、催款、查发货进度 |
| **采购（国内）** | 供应商 + 采购单 + 到货 | 按 BOM/备货计划下单、跟交期、对账 | 采购与销售订单脱节（卖出去才发现没料）；到货数量与质检结果不联动 | 询价比价、下 PO、跟催、收货质检、供应商对账 |
| **仓储（国内仓 + 海外仓）** | 出入库执行 | 收发货不重不漏、库存账实一致、扫码作业 | 出库单要求绑销售订单（B2B 对），但海外仓补货入库没有对应单据类型；批次/效期靠纸 | 收货上架、拣货出库、盘点、头程到仓签收、海外仓调拨 |
| **财务** | 收付款 + 发票 + 费用 + 物流签收支付 | 单据齐全才付款、汇率口径统一、对账有据 | 物流费四级审批到财务才算完，但费用分摊不到订单/SKU；平台结算单对不上 | 审核物流费用、确认收款、开票、月末结账 |
| **运营（亚马逊/TikTok）** | 平台账号 + 只读订单/库存 | 实时知道 FBA 可售/在途、断货预警、补货建议一键转采购 | 要去各站点后台来回切；补货量靠拍脑袋；多站点多账号数据不在一处 | 每日看销量与库存、发起补货、跟踪头程到仓 |
| **系统管理员** | 账号/权限/同步配置 | 权限最小化、操作可追溯、同步失败可感知 | 同步卡住无人知；凭据分散 | 建号授权、配置平台凭据、排查同步异常 |

### 2.2 权限与职责边界（需求约束）

- **数据可见性按业务线隔离**：销售只看自己客户/订单；运营只看平台域；仓储只看库存与出入库；财务可看全域金额但不可改单据金额；老板全域只读 + 审批。
- **审批人不可自审**：物流单"提交人 ≠ 校对人 ≠ 审批人 ≠ 财务签收人"（现有代码已按角色字段校验，见 3.5）。
- **越权写操作必须留痕**：现有 `AuditLog` 模型存在，但需扩展覆盖范围（见 NFR）。

## 3. 业务域拆解与功能需求

> 分级说明：**M**=Must（无此不能上线）、**S**=Should（首年应有）、**C**=Could（有余力再做）
> 管理属性：**【管】**=ERP 主动管理（写）、**【镜】**=只读镜像（读）、**【辅】**=辅助决策

### 3.1 域 A：阿里国际 B2B 域（核心，ERP 为权威源）

**主流程**
```
询盘 Inquiry → 报价 Quotation（多次改价/版本） → 客户确认 → 销售订单 Order
   → [审批（超限价/超账期）] → 生产/备货 ProductionRecord → 出库单 OutboundOrder（必须绑订单）
   → 装箱发运 Shipment（可多次分批发运） → 报关/单证 Invoice(PI/CI)
   → 收款 Payment（可多笔、可预收+尾款） → 订单完成；异常→退货/换货
```
**关键业务规则（来自业务模式说明，必须硬约束）**
- R-A1：出库单**必须**关联销售订单，不允许"无源出库"。
- R-A2：出库仓库可以是国内仓，也可以是海外仓（B2B 也可从海外仓就近发货）。
- R-A3：支持**分批出库**（一单多出库单），累计出库量 ≤ 订单量；超发必须显式审批。
- R-A4：订单金额锁定后，改价/改量必须留版本痕迹并触发重审批。
- R-A5：币种以订单为准，收款可跨币种，需按订单汇率折算本位币。

### 3.2 域 B：亚马逊 / TikTok 平台自营域（只读镜像）

**业务实质**：卖出去、发货、退款全部由平台完成。ERP **不创建**零售订单、**不发起**发货、**不干预**平台库存。ERP 存在的意义是把平台数据搬回来，用于：销量分析、库存预警、补货决策、利润核算。

**清晰的"做 / 不做"边界**

| 平台侧动作 | ERP 是否管 | 理由 |
|---|---|---|
| 零售订单生成 | ❌ 不管（只镜像） | 平台权威 |
| 零售发货 / 退货处理 | ❌ 不管（只镜像状态） | FBA/平台仓履约 |
| FBA 可售/预留/在途库存 | ❌ 不改（只镜像快照） | 平台权威，改了也没用 |
| 自有海外仓实物库存 | ✅ 管 | 本公司资产 |
| 补货数量决策、发补货指令 | ✅ 管 | 需 ERP 建议 + 人工确认 |
| 头程物流下单与费用 | ✅ 管 | 需四级审批 |
| 平台费用（佣金/仓储/广告）归集 | ✅ 管（只读汇入 + 分摊） | 影响真实利润 |
| Listing 内容/价格/广告 | ⚠️ 弱管（现有 ads 域 + 采集发布） | 属营销域，与 ERP 主流程解耦 |

### 3.3 域 C：海外仓库存域（ERP 主动管理）

**为什么必须自己管**：FBA 之外的第三方海外仓（美/英/德/阿联酋）是公司实物资产，平台不知道、也不管。这里的账实不符会直接变成断货或呆滞。

**主流程**
```
头程到仓签收 → 海外仓入库（按箱/按 SKU，含批次） → 库存可用
   → 平台补货（从海外仓发 FBA，出库） / B2B 就近发货（出库）
   → 周期盘点（盘盈盘亏调整）
```

### 3.4 域 D：补货 / 头程物流域（ERP 主动管理）

**业务实质**：把货从国内仓（或工厂）搬到海外仓/FBA。这是公司**现金流占用最大、审批最重**的环节（海运费一笔几万到几十万），也是现有系统做得最完整的一块（四级审批）。

**主流程**
```
补货建议（销量预测 + 现有库存 + 在途 + 安全库存）
  → 补货计划（人工确认数量/批次/目的仓）
  → 头程物流订单 LogisticsOrder（选服务商、比价、费用明细）
  → 四级审批：提交人 → 校对人 → 审批人 → 财务签收支付
  → 订舱发运（IN_TRANSIT）→ 到港清关 → 海外仓签收（ARRIVED/DELIVERED）
  → 海外仓入库单（库存增加，闭环）
  → 费用归集：分摊到 SKU 单位成本
```

### 3.5 域 E：国内采购域（ERP 主动管理）

**业务实质**：向工厂/供应商订原料与成品（自有工厂则部分是生产工单）。采购是 B2B 交付与海外备货的**共同上游**。

**主流程**
```
需求（B2B 订单缺料 / 补货计划 / 安全库存触发）

  → 供应商对账 → 付款 → PO 关闭
```

## 4. 全局共性需求

### 4.1 主数据（三条业务线的唯一交汇点）
- **产品/SKU 单一主数据**：一个 SKU 可对应多个平台 ASIN/FNSKU、多个供应商料号。必须建独立映射表（现无），否则库存、销量、成本无法对齐。
- **仓库主数据统一**：国内仓与海外仓应统一在"仓库"概念下（含类型、时区、币种、是否平台仓），而不是两张互不相干的表。
- **客户/供应商去重与合并**：现有同步逻辑会自动创建 `平台名-Customer-订单号` 客户，必须禁止。

### 4.2 单据编号与可追溯
- 统一语义编号：`SO-/QU-/PO-/OUT-/IN-/LO-/SHIP-` + 日期 + 序列。
- 每笔库存变动必须能反查到源单据与操作人（现有 `InventoryLog.referenceType/referenceId` 可支撑，海外侧缺失）。

### 4.3 利润口径统一
四个成本项必须能落到订单/SKU 级：**采购成本 + 头程分摊 + 平台佣金/仓储 + 广告费**。当前分散在采购、物流、平台、广告四个模块，未汇总。

### 5.3 缺口归类结论

- **需新建的域**：海外仓库存域（G3/G9/G17）、补货计划域（G6/G12）、平台镜像域（G2/G4/G5/G11）。
- **需改造的域**：同步框架（G1/G13/G14 落库目标与多账号）、库存键规范（G8）、审批引擎泛化（G10）。
- **可复用的成熟资产**：B2B 订单-出库闭环、国内采购链、物流四级审批、RBAC、报表骨架。

### 5.4 三条关键设计裁决（建议写入架构决策记录）

1. **`Order` 与 `PlatformOrder` 严格分离**：`Order` 只存 B2B；平台零售一律进 `PlatformOrder`，且**永不**产生 `OutboundOrder`。同步管线需按 `platformCode` 分流写库（alibaba→Order，amazon/tiktok→PlatformOrder）。
2. **库存三层模型**：`InventoryItem`（国内，受 `Warehouse` 约束）｜`OverseasInventory`（海外实物，受 `OverseasWarehouse` 约束）｜`PlatformInventorySnapshot`（FBA/平台仓只读快照，按站点按日留存）。对外提供"统一可用库存"视图，但写入始终回到各自权威层。
3. **单据关联泛化**：`LogisticsOrder` 引入 `bizType`（SALES_SHIPMENT / REPLENISHMENT / TRANSFER）+ `refIds`，并新增 `inboundOrderId`；`InboundOrder` 增加 `overseasWarehouseId` 与 `logisticsOrderId`，使"补货→物流→到仓入库"成为一条可追溯链。

## 6. 非功能需求

### NFR-1 多站点多币种
- 站点维度必须是一等公民：`(platform, marketplace, shop)` 三元组唯一标识账号；每站点独立币种、时区、结算周期。
- 交易币种（USD/EUR/GBP/AED/CNY）+ 本位币（CNY）双列记账；汇率取"业务发生日"快照并保留历史表，禁止用实时汇率回算历史报表。
- 金额一律 `Decimal(12,2)`（现有 schema 已遵循），禁止 float；汇总层明确"含税/不含税"。
- 时区：平台时间为站点本地时间，入库统一 UTC，展示按用户/站点时区转换；跨时区日切（如美西 vs 迪拜）需在日报口径中定义清楚。

### NFR-2 审批合规
- 审批链与金额阈值可配置（`ApprovalWorkflow` 已具备配置能力，需扩展到采购、B2B 订单让价）。
- 四眼原则：提交/校对/审批/财务签收不可同一人；管理员代操作必须记录原因。
- 审批快照：审批时的单据内容需冻结留档（现仅记录动作，不记录被审内容版本），以应对事后争议。
- 全量审计：所有金额、库存、状态变更写 `AuditLog`（含 before/after、IP、UA），审计日志不可删除、保留 ≥ 3 年。

### NFR-3 数据一致性
- 库存扣减必须"校验 + 扣减"在同一事务内，并用乐观锁重试（现有 `version` 机制保留，建议补最大重试与失败告警）。
- 同步幂等：以 `(platform, accountId, platformOrderId)` 唯一键做 upsert，重放不产生重复单（现有 `Order` 仅靠 `findFirst` 判重，且无唯一索引，存在并发重复风险）。
- 平台数据与 ERP 数据"以平台为准"的字段（订单状态、FBA 库存）单向覆盖；"以 ERP 为准"的字段（本地成本、库位、备注）禁止被同步覆盖——需字段级白名单。
- 关键链路的最终一致：补货单 → 物流单 → 到仓入库 → 海外库存，任一环缺失需有"在途/待处理"视图兜底，不允许数据凭空消失。
- 对账机制：每日自动比对（库存台账 vs 流水汇总、平台订单 vs 结算单），差异生成待办。

### NFR-4 性能与容量
- 列表接口分页上限 100（现有 `Math.min(limit, 100)` 已符合）；平台订单按日分区/归档，保留 24 个月热数据。
- 同步任务限流（SP-API 有严格 rate limit，需令牌桶 + 指数退避；现有 `order-sync` 已有重试骨架）。
- 仪表盘查询走聚合表/物化视图，避免跨 4 站点实时扫单。

### NFR-5 安全与权限
- 平台凭据加密存储（现有 `encryptCredentials`/`decryptCredentials` 已具备），密钥不入库不出日志。
- 最小权限 + 数据行级隔离（销售只看自己客户，运营只看自己站点）。
- 敏感操作（改价、作废、库存调整）二次确认 + 审批。

### NFR-6 可运维性
- 同步健康度看板：每平台最后成功时间、失败次数、积压条数；失败连续 N 次告警（现有仅 `PlatformSyncLog`，无告警）。
- 调度需支持多实例（DB 锁或分布式锁），或明确"仅单实例运行"并加启动互斥。
- 数据备份与恢复演练（库存与财务为核心）。

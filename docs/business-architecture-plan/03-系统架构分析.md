## 1. 现状架构盘点

### 1.1 技术栈与部署形态

| 层 | 现状 | 备注 |
|---|---|---|
| 运行时 | Next.js 16（App Router），Node 侧 Route Handler 即后端 | 无独立后端服务，业务逻辑与 HTTP 层同进程 |
| ORM | Prisma 6，`prisma/schema.prisma` 单文件单一 schema | 兼用 `migrate dev` 与 `db push`，迁移历史仅 7 个，说明大量变更走 `db push` |
| 数据库 | PostgreSQL（Docker 网络内） | 无读写分离、无分区、无物化视图 |
| 部署 | Docker / docker-compose 单容器 | **同步调度器是进程内 `setInterval`**，多副本部署会重复拉单（见 §1.7-P6） |
| 认证/授权 | `getUserFromRequest` + `User/Role/Permission/UserRole/RolePermission` 自建 RBAC | 路由层手写校验，与业务校验混在 route 内 |
| 校验 | Zod（`src/lib/api-schemas.ts`、`src/lib/validators`） | 新旧两套 API 并存，校验覆盖不一致 |
| 统一响应 | `successResponse / errorResponse`（`src/lib/api-response.ts`） | `/api/v1/*` 遵循，旧 `/api/*` 部分裸返回 |

**分层实况**：名义上是"Route → Service → Prisma"，实际上不存在 service 层。多数 route 直接开 `prisma.$transaction` 写多张表（如入库确认、出库批量、收货），可复用逻辑抽取到 `src/lib/inventory-utils.ts`、`currency-utils.ts`、`order-status-machine.ts` 等工具函数。**这是后续所有改造的约束：新增的业务不变量（库存不为负、账实一致）目前没有单一收口点。**

API 路径呈"双轨"：
- 旧轨 `/api/{orders,purchases,products,customers,...}`（早期模块，直连页面）
- 新轨 `/api/v1/{inventory,inbound-orders,outbound-orders,purchase-orders,logistics,reports,ads,...}`（v1 契约）

平台同步入口在旧轨：`/api/sync`、`/api/sync/config`、`/api/sync/status`、`/api/sync/test`。

### 1.2 数据模型全景（按业务域）

91 个 model 可归为 9 个域。与本次任务相关的核心域如下。

**A. 销售域（B2B 主干）**

| `Payment` / `Invoice` | `orderId`、`currency`、`exchangeRate` | 发票与回款 |

**B. 采购域**

### 1.3 核心链路实况

**① B2B 销售 → 出库（唯一闭环完整的链路）**

```
Inquiry → Quotation → Order(PENDING→CONFIRMED→…) → OutboundOrder(必需 orderId)
   → 扣减 InventoryItem(order.warehouseId 维度, version 乐观锁) → InventoryLog(OUT)
   → Shipment(可选) → Order.shippedQty/deliveredQty 累加
```

`OutboundOrder.orderId` 为必填且 `onDelete: Cascade`，因此**不存在"无销售订单的出库"**。这是当前 B2B 强约束，也是平台 FBM 履约无法复用的原因。

**② 采购 → 入库（半闭环：账面能走通，但仓库维度是脏的）**

```
PurchaseOrder(可挂 salesOrderId) → PurchaseReceipt(warehouse String) 
   → 另一条腿：InboundOrder(PURCHASE_IN) → confirm → InventoryItem + InventoryLog(IN)
```

两条收货路径（`PurchaseReceipt` 与 `InboundOrder`）**并存且互不同步**：`PurchaseReceiptItem` 有 `acceptedQty/rejectedQty`，`InboundOrderItem` 有 `expectedQuantity/actualQuantity`，`PurchaseOrderItem.receivedQty` 由谁累加取决于走哪条路径。这是"同一事实两个写入方"的典型账实风险。

**③ 物流审批**：`LogisticsOrder` 独立 4 级状态机，通过 `salesOrderId` 弱关联销售订单（无 FK），与 `Shipment`、`InboundOrder` 均无关联 → **海外备货的"物流在途"无法回填到库存的在途量**，补货引擎缺一条腿。

**④ 平台同步（只读，写销售订单）**

```
initSyncScheduler() ── setInterval(platformCode) ──┐
/manual /api/sync ────────────────────────────────┤
                                                   ▼
                          executePlatformSync(platformCode, trigger)
                                                   ▼
                    platformRegistry.get(platformCode) → Adapter
                                                   ▼
                       fetchOrders() → UnifiedOrder[] → processSingleOrder()
                                                   ▼
          prisma.order.findFirst({platformOrderId, sourcePlatform})  ← 无唯一约束
                    ├─ 存在 → 仅按 STATUS_MAP 单向推进 status
                    └─ 不存在 → findOrCreateCustomer() → prisma.order.create()
                                                   ▼
                                            PlatformSyncLog
```

`AmazonAdapter` 已实现 LWA 换 token + SigV4 签名 + `REGION_MAP(na/eu/fe)`，方法集：
- `fetchOrders` / `fetchOrderDetail`（`/orders/v0/orders`）
- `fetchFbaInventory`（`GET /fba/inventory/v1/summaries`，`granularityType=Marketplace`）
- `fetchListings`（`GET /listings/2021-08-01/items/{sellerId}`，需 `sellerId`）

**`fetchFbaInventory` 与 `fetchListings` 在 `src` 中 0 处调用**——能力已具备，但既无落库模型也无调度任务，属"实现的空转能力"。`tiktok.ts` / `shopify.ts` 各 36 行，均为占位。

## 2. 目标架构设计

### 2.1 设计原则

1. **单一事实源（Single Source of Truth）**：每个业务事实只有一处权威存储；平台侧事实以平台为权威，本地只做**镜像**，不改本地账。
2. **库存是一个账本，不是几张表**：位置（location）维度化，国内仓/海外仓/平台仓统一进账本，用 `authority` 字段区分"谁说了算"。
3. **只读边界显式化**：平台适配器只暴露 GET；写能力作为 `capabilities` 声明，第三期才开。
4. **幂等优先**：所有跨系统写入（同步、入库确认、对账调整）必须有幂等键；余额可由流水重算（`SUM(ledger)` == `balance`）。
5. **金额三件套**：单据币种原值 + 生效汇率快照 + 本位币金额，永不跨币种聚合原值。
6. **不推倒重来**：沿用 Prisma 单 schema、`/api/v1` 契约、`successResponse`、RBAC、`AuditLog`；旧表通过迁移脚本与只读兼容层退役，不做大爆炸切换。

### 2.4 同步层设计

#### 2.4.1 存储策略：快照表 vs 实时查询 → **快照优先**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 实时透传（每次页面请求打 SP-API） | 无冗余 | SP-API `fba/inventory` 限流严（突发即 429）、页面延迟秒级、无历史、无法离线对账 | ✗ |
| B. 仅存最新态（upsert 覆盖） | 表小、查询快 | 无法回溯"昨天为什么补货"、无法算 ADS 趋势、对账争议无证据 | ✗ |
| **C. 追加式快照 + 日聚合（推荐）** | 可回溯、可复算、可与本地台账按时点对账、天然幂等（唯一键含 `capturedAt`） | 需 TTL 治理 | ✓ |

落地细则：
- **采集频率**：订单 15 min；FBA 库存 60 min（可配）；Listings 6 h；销售日聚合每日 02:00（站点时区）。
- **保留策略**：`PlatformInventorySnapshot` 明细 90 天；`PlatformSalesDaily` 永久；超期快照按日折叠为 `max(capturedAt)` 一条。
- **读取路径**：页面/引擎一律读**库**，绝不直连平台；"最新态" = 当日子查询取 `capturedAt` 最大值。
- **失效标记**：`SyncJob` 记录 `dataFreshness`，超过阈值（如 3× 周期）在 API 响应里带 `stale: true`，前端显示"数据可能不是最新"。

#### 2.4.2 调度：DB 驱动 + 分布式锁

替代现状 `setInterval(platformCode)`：

```prisma
model SyncJob {
  id            String   @id @default(cuid())
  platformCode  String
  marketplaceId String?
  jobType       String            // ORDERS | INVENTORY | LISTINGS | SALES_AGG

  recordsFailed Int      @default(0)

  retryCount    Int      @default(0)
  lockToken     String?           // 行级锁持有者
  lockedUntil   DateTime?

  @@unique([platformCode, marketplaceId, jobType, scheduledAt])  // 同一时刻只排一个

model SyncCursor {
  id            String   @id @default(cuid())
  platformCode  String
  marketplaceId String
  resource      String            // orders | fba_inventory | listings
  watermarkAt   DateTime?         // 已同步到的时间点
  pageToken     String?           // 分页/续传 token
  overlapMin    Int      @default(15)  // 回溯窗口，防边界漏单

```

执行模型：
1. 调度入口只做"生成待执行 `SyncJob` 行"（幂等唯一键），可由容器内每 60s 的 tick 或外部 cron 触发。
2. Worker 抢单：`UPDATE sync_jobs SET status='RUNNING', lockToken=$1, lockedUntil=now()+interval '10 min' WHERE id=(SELECT id FROM sync_jobs WHERE status='PENDING' AND scheduledAt<=now() ORDER BY scheduledAt LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *` —— 多副本安全。
3. 失败按指数退避重排（`retryCount`，上限 5），`lockedUntil` 过期可被重新抢占（进程崩溃自愈）。
4. `PlatformSyncConfig.isSyncing` 从"互斥锁"降级为"展示状态"，不再承担并发控制。

#### 2.4.3 多站点（marketplaceId 维度）

- **配置粒度**：`PlatformSyncConfig @@unique([platformCode, marketplaceId])`，一个亚马逊账号下 4 个站点 = 4 条配置，共用 `PlatformAccount` 的 LWA 凭据（凭据上移，见下）。
- **凭据与站点分离**：`PlatformAccount` 保存 LWA `clientId/clientSecret/refreshToken`（账号级），新增 `marketplaceId` 字段表示"该账号的主站点"或多个 `PlatformAccountMarketplace` 关联行；适配器入参改为 `{ accountId, marketplaceId }` 而非仅 `platformCode`。
- **适配器签名演进**（向后兼容）：

### 2.5 业务层：补货建议引擎

#### 2.5.1 两级补货模型（必须分开算，不能混）

| 层级 | 场景 | 目的仓 | 来源 | 提前期 LT 构成 |
|---|---|---|---|---|
| **L1 采购补货** | 供应商 → 国内仓 | `DOMESTIC` | `PurchaseOrder` | 供应商 `leadTime` + 质检 + 入仓 |
| **L2 头程补货** | 国内仓 → 海外仓 | `OVERSEAS` | `InboundOrder(TRANSFER_IN)` + `LogisticsOrder` | 备货 + 头程 `transitDays` + 清关 + 上架 |
| **L3 平台补货** | 海外仓 → FBA | `PLATFORM_FBA` | `InboundOrder(PLATFORM_INBOUND)` | 海外仓处理 + 平台入仓上架（用 `inboundWorking/Shipped/Receiving` 校准） |

同一 SKU 的三层需求**串联而非叠加**：L3 的需求驱动 L2，L2 的在途驱动 L1。若三层都用同一 ADS 独立计算，会出现重复下单（典型错误）。

#### 2.5.2 计算口径

```
# 1) 销售速度（加权，抗短期波动；缺数据自动降级）
ADS = 0.5*avg(units, 7d) + 0.3*avg(units, 30d) + 0.2*avg(units, 90d)
      （若 7d 无数据 → ADS = avg30；若 30d 也无 → avg90；全无 → 不生成建议，标记 NEW_SKU）

# 2) 需求波动（日粒度标准差）
σ_d = stddev(daily units, 90d)

# 3) 安全库存（服务水平法，z: 90%→1.28, 95%→1.65, 97.5%→1.96）
SS  = ceil(z * σ_d * sqrt(LT + RC))        # RC = reviewDays，补货评审周期

# 4) 补货点
ROP = ADS * (LT + RC) + SS

# 5) 可用量（承诺口径，注意三项都要算）
ATP = onHand - reserved + inboundShipped          # inboundShipped = 已发未到（入库单 IN_TRANSIT）
      （FBA 位置：ATP = platformAvailable + inboundShippedQty + inboundReceivingQty）

# 6) 建议量
target   = ADS * (LT + RC + coverDays) + SS
raw      = target - ATP
suggested= raw <= 0 ? 0 : roundUpToMOQ(ceil(raw), moq, 装箱率)
```

边界规则（写入引擎，不留给人工）：
- `ATP < ROP` 才生成建议（否则 0），`ATP <= 0` 置 `URGENT` 标记。
- 新品/无销售历史：用同类目均值或人工指定 `initialStock`，`reason=NEW_SKU` 显式标注，**不允许静默按 0 处理**（0 会导致永不补货）。
- 供应商 `moq` 与 `装箱率` 取 `ProductSupplier`（优先 `isPreferred`），缺失则回落到 `Product.moq`。
- 季节性/促销：`paramsSnapshot.uplift` 乘数，人工在计划单上填，引擎记录在快照里以便复算。
- 停售/清仓（`Product.status != ACTIVE`）：不生成建议，已有在途单进"清仓消化"列表。

#### 2.5.3 数据流与幂等

```
SyncJob(ORDERS/SALES_AGG) → PlatformSalesDaily ─┐
SyncJob(INVENTORY)         → PlatformInventorySnapshot ─┤
InventoryBalance/InventoryLedger（本地台账）             ├─▶ ReplenishmentEngine.run(date, warehouseId)
InboundOrder(IN_TRANSIT)   → 在途                       │        │
PurchaseOrder(pending)     → 在途（L1）                 │        ▼
ProductSupplier(leadTime, moq) ────────────────────────┘   ReplenishmentPlan(DRAFT)
                                                                   │ 人工复核/调整 finalQty
                                                                   ├─▶ 审批（复用 ApprovalWorkflow）
                                                                   ├─▶ 生成 PurchaseOrder（L1）
                                                                   └─▶ 生成 InboundOrder(TRANSFER_IN/PLATFORM_INBOUND)（L2/L3）
```

- 幂等：`@@unique([planDate, targetWarehouseId, planType])`，同日重跑 = 更新 DRAFT 计划（已 `ORDERED` 的不可覆盖）。
- 可复算：`paramsSnapshot` 存输入（ADS、σ、LT、ATP 明细、参数版本），三个月后能解释"为什么当时建议 500 件"。
- 性能：单仓 5k SKU 应在秒级完成 —— 用一条 SQL 预聚合 `PlatformSalesDaily` + `InventoryBalance` + 在途，再在 Node 侧算，**禁止 N+1 逐 SKU 查**。

## 3. 关键架构决策

### ADR-01 库存模型：统一账本 vs B2B/平台双轨

| 选项 | 说明 | 评价 |
|---|---|---|
| A. 保持 `InventoryItem` + 复活 `OverseasInventory` | 改动最小 | ✗ 两套并发控制、两套流水、报表要 union；FBA 与海外仓还要第三套 |
| B. 统一 `InventoryBalance` + `InventoryLedger`，位置维度化 | 一次重构 | ✓ 单一不变量收口，对账/补货/报表一个口径 |
| C. 完全事件溯源（无余额表） | 最纯粹 | ✗ 每次查询要 aggregate，页面性能不可接受 |

**决策：B**。余额表是物化的快照（可重建），流水是事实。`warehouseId` 全程 FK，杜绝字符串仓库。代价是 P1 期必须做数据迁移与全量回归（出库、入库、报表三处），收益是后续所有功能不再各自造库存表。

### ADR-02 双账对账模式：本地台账 vs 平台镜像

**原则：一账一主（single writer per location），差异只出工单，不自动改账。**

| 位置类型 | `authority` | 谁写 | 平台数据角色 |
|---|---|---|---|
| 国内仓 / 海外仓 | `LOCAL` | ERP（入库/出库/调拨/盘点） | 无（不看平台） |
| 平台 FBA 仓 | `PLATFORM` | 平台（SP-API） | 权威；ERP 只写 `PlatformInventorySnapshot` 与 `InventoryBalance(authority=PLATFORM)` 的镜像值，**不参与 ERP 出库扣减** |

对账流程（每日 03:00，按 `(warehouseId, productId)`）：

```
platformQty = 最新快照 available + inboundShipped（口径必须与本地定义对齐，写死在引擎里）
localQty    = InventoryBalance.onHand
diff        = platformQty - localQty
|diff| <= tolerance → 跳过
否则 → InventoryReconciliation(PENDING) + 通知
处理：ACCEPTED（确认差异，调整本地镜像）/ ADJUSTED（生成 ADJUST_UP/DOWN 分录，需审批）/ IGNORED（带原因，7 天后可再提）
```

三个必须守住的点：
1. **平台镜像绝不反写 B2B 台账**。FBA 的"可用"与海外仓的"实存"是不同物理位置的量，混算会双计。
2. **对账口径固化**：`available + inboundShipped` vs `onHand`，若亚马逊改口径（如引入 `inboundReceiving`），必须在引擎里改一处而非散落各处。
3. **差异不静默**：所有 `ADJUST_*` 分录带 `refType=RECON` + 审批人，可审计。

### ADR-03 平台订单落库位置：写 `Order` 还是 `PlatformOrder`

**决策：`PlatformOrder` 为平台订单唯一落库点；`Order` 只承载需要 ERP 内部履约的销售订单。**

- 现状问题：同步直写 `Order`，导致平台零售订单进入 B2B 的客户/回款/信用/出库语境，`Order.customerId` 必填迫使 `findOrCreateCustomer` 为每个买家造客户（实测代码里用 `${platformCode}-Customer-${orderId}` 兜底命名，客户表会被污染）。
- 目标：`PlatformOrder` 加 `marketplaceId`、`settlementId`、`rawPayload Json`，作为分析/利润/对账的数据底座；**仅当该订单需要 ERP 发货（FBM/海外仓自发）时**，才创建 `Order`（`sourcePlatform` 保留）并通过 `PlatformOrder.internalOrderId` 双向回链。
- 对现有数据：保留 `Order.sourcePlatform` 字段并加 `@@unique([sourcePlatform, platformOrderId])`（修 P5）；存量平台订单做一次"归位"脚本（按 `sourcePlatform IS NOT NULL` 迁至 `PlatformOrder`，`Order` 行标记 `archived` 而非删除，避免破坏历史出库/回款引用）。
- 收益：B2B 报表口径干净；4 站点订单可按 `marketplaceId` 直接切分；平台费用/佣金进 `PlatformOrder` 而不污染 `Order.totalAmount`。

### ADR-04 平台数据存储：快照优先，实时透传仅作兜底

**决策：追加式快照 + 日聚合；页面与引擎只读库。**

理由：SP-API 限流（`fba/inventory` 0.5 rps / burst 2）使实时查询在并发下必然 429；补货引擎需要 7/30/90 天时间序列，实时接口不提供历史；对账需要"某时点的平台数"作为证据。代价是快照表体积（估算：5k SKU × 4 站点 × 24 次/天 ≈ 48 万行/天，按 90 天保留 ≈ 4300 万行）——必须按 `capturedAt` 月分区或定期折叠，这一条要在 P2 前定好，否则后期改分区要停机。

### ADR-05 多币种金额处理

**决策：单据三件套（原币金额 + 汇率快照 + 本位币金额）+ 独立 `FxRate` 表；禁止跨币种直接加总。**

- 本位币统一 **CNY**（与 `Account/Transaction.amountCny` 一致）。
- 每个金额单据/行补 `currency`、`exchangeRate`、`amountBase`；已有 `Order`/`PurchaseOrder` 符合，`InboundOrder`/`LogisticsOrder`/`OverseasInventory.costPerUnit` 需补。
- 汇率写入即冻结：单据创建时从 `FxRate` 取当日值存入 `exchangeRate`，**后续汇率变动不回写历史单据**（否则毛利会随汇率漂移，无法解释）。
- 汇总统一走 `amountBase`；报表如需展示原币，按币种分组，不做换算后相加。
- `Decimal(12,2)` 保金额、`Decimal(10,6)` 保汇率、`Decimal(18,8)` 保汇率表精度；JS 侧禁止 `parseFloat` 参与金额运算（现状 `currency-utils.ts` 用 `Math.round(x*100)/100` 是浮点近似，应改 `Prisma.Decimal` 或整数分）。
- 亚马逊结算含多币种（站点币 + 结算币），`PlatformOrder` 需 `marketplaceCurrency` 与 `settlementCurrency` 两字段，否则利润报表口径必错。

### ADR-06 调度：DB 驱动作业表 + 分布式锁

**决策：`SyncJob` 表 + `FOR UPDATE SKIP LOCKED` 抢单，替代进程内 `setInterval`。**
理由：Docker 多副本/滚动发布下进程内定时器必然重复执行；重启丢调度；`isSyncing` 布尔锁在崩溃后会永久卡死（无超时释放）。代价是引入一个 tick 循环（60s 一次，开销可忽略）。顺带获得可观测性（作业历史、成功率、耗时分布），这本身是运维刚需。

### ADR-07 幂等贯穿

**决策：跨系统写入必须有幂等键。** `InventoryLedger.idempotencyKey` uniq、`SyncJob` 唯一键、`ReplenishmentPlan` 唯一键、HTTP `Idempotency-Key`。理由：同步重试、用户双击、网络超时重发都是常态；库存错账的修复成本远高于加一个唯一约束。

## 4. 演进路径（三期）

### 第一期：库存账本 + 海外仓 + 入库 + 采购闭环（4–6 周）

**范围**
1. `Warehouse` 扩展（`type/authority/country/timezone/leadTimeDays/platformCode/marketplaceId`），`OverseasWarehouse` 数据并入后废弃。
2. 新建 `InventoryBalance` + `InventoryLedger`；`InventoryItem`/`InventoryLog` 迁移（双写过渡 1 个迭代后切读）；删除 `StockMovement`。
3. 仓库字符串清洗：`'MAIN'` → 建真实默认仓；`Warehouse.id`/`code` 混用统一为 `id`，生成映射表并出清洗报表（**迁移前必须人工确认映射**，这是不可自动化的部分）。
4. `InboundOrder` 改造：`warehouseId` 必填 FK、`type` 扩展（`TRANSFER_IN`/`PLATFORM_INBOUND`）、币种三件套、`logisticsOrderId` FK、状态机（`DRAFT→SUBMITTED→APPROVED→IN_TRANSIT→ARRIVED→RECEIVED`）。
5. `LogisticsOrder` 补 `exchangeRate` + `salesOrderId` FK + `inboundOrders` 反向关系；物流审批通过的入库单可回填 ETA。
6. 采购闭环收敛：以 `InboundOrder` 为唯一收货过账入口，`PurchaseReceipt` 降级为验收明细或停用（消 P10）。
7. `InventoryService` 抽出（记账/预留/释放/调拨双分录），出库、入库、收货三条路径全部改走它。
8. `FxRate` 表 + 汇率写入冻结逻辑。
9. API：`/v1/warehouses`、`/v1/inventory/{balances,ledger,adjustments,transfers}`、`/v1/inbound-orders`（含 confirm/cancel）、`/v1/fx-rates`。

**依赖**：无（可独立开工）。**但需业务先确认**：`'MAIN'` 归属哪个真实仓、海外仓清单与其 `authority`、历史入库单是否都要补 `warehouseId`。

**退出标准**
- 迁移后 `SUM(InventoryLedger.qtyDelta) == InventoryBalance.onHand` 全量对平（0 差异）。
- 新旧库存报表数字逐仓逐 SKU 一致。
- 国内仓 → 海外仓调拨可完整走通（调拨单 → 出库 → 头程物流单 → 入库确认 → 海外仓余额增加）。
- 出库超卖被 `InventoryService` 拦截（并发出库测试：并发 20 请求扣同一 SKU，成功数 = 可用量）。

### 第二期：补货建议 + 平台数据对账（4 周）

**范围**
1. `SyncJob`/`SyncCursor` + DB 驱动调度（替换 `setInterval`）；`PlatformSyncLog` 保留为聚合视图。
2. `PlatformSyncConfig` 加 `marketplaceId`（`unique([platformCode, marketplaceId])`）；`PlatformAccount` 保存账号级 LWA。
3. FBA 库存/Listings 落库：`PlatformInventorySnapshot`、`PlatformListingSnapshot`；接线已存在但空转的 `fetchFbaInventory`/`fetchListings`（含分页 token 持久化）。
4. `PlatformSalesDaily` 日聚合（从 `PlatformOrder`/`Order` 汇总，站点时区归日）。
5. `InventoryReconciliation` + 每日对账任务 + 差异工单 API/页面。
6. `ReplenishmentEngine` v1：先做 **L3（海外仓→FBA）**，再做 **L2（国内→海外仓）**；`ReplenishmentPlan(Item)` + 审批 + 一键生成 `InboundOrder`。
7. API：`/v1/platform/{inventory,listings,sales}`、`/v1/sync/{jobs,cursors}`、`/v1/inventory/reconciliations`、`/v1/replenishment/*`。

**依赖**：第一期完成（账本与在途口径是引擎输入）。**并行前置**：SKU 映射（`sellerSku/fnsku → productId`）必须有维护入口，否则快照全是 `productId=null`，补货引擎无输入——这是本期最常见的隐性阻塞，建议第一期就建映射表。

**退出标准**
- 4 站点（或先 1 站点试点）FBA 库存连续 7 天快照无缺失，`stale` 告警可用。
- 对账任务每日产出差异清单，`tolerance` 内自动通过；差异可追溯到具体 SKU 与快照。
- 补货计划对 20 个 SKU 的人工判断一致率 ≥ 80%（抽样复核），计划可复算（同输入同输出）。
- 计划 → 采购单/入库单可一键生成，生成后计划锁 `ORDERED` 不可篡改。

### 第三期：多站点扩展 + 写操作（4–6 周）

**范围**
1. 4 站点全量上线：账号/站点/仓库/Listing 一一对应；站点级权限与数据隔离（`row-level-filter.ts` 复用）。
2. 平台写操作：Listings 价格/库存推送、FBA 入库货件创建（`POST /fba/inbound/v0/shipments`）、发货确认；全部走 `capabilities.write` 白名单 + 二次确认 + 审计。
3. 写操作的对账闭环：推送后回读校验（写 → 读回 → `PlatformListingSnapshot` 对比），失败入重试队列，**不允许"发送成功即认为生效"**。
4. 平台单据接入通用 `ApprovalWorkflow`（消 P13），`LogisticsOrder.approvalStep` 兼容期保留。
5. 成本与利润：头程费用按 `InboundOrder` 分摊到 SKU 落地成本；`ProfitDetail` 改用 `amountBase` + 站点币双口径。
6. 可观测性：同步成功率/延迟看板、对账差异趋势、补货计划执行率（建议量 vs 实际下单量）。

**依赖**：第二期（快照、对账、站点维度）。**风险最高**：写操作涉及平台合规与不可逆动作（改价、建货件），必须灰度 + 白名单 SKU + 每日限额。

**退出标准**
- 写操作有完整审计链（谁、何时、改前值、改后值、平台回执）。
- 单站点故障不影响其他站点同步（隔离验证）。
- 落地成本可算到 SKU 级，毛利与财务手工账差异 < 1%。

## 5. 风险与前置条件

| 风险 | 影响 | 缓解 |
|---|---|---|
| `'MAIN'` 等悬空仓库字符串无法自动映射 | P1 迁移阻塞 | 先跑一次"仓库字符串分布"报表，人工出映射表；无法归属的历史数据入"待定仓"，不阻断迁移 |
| 平台订单存量已写入 `Order` | 归位脚本可能破坏出库/回款引用 | 归档而非删除；`internalOrderId` 回链；先在测试库跑全量 diff |
| 快照表体积（4 站点 × 90 天） | 查询变慢、磁盘压力 | P2 前定分区/折叠策略；`PlatformInventorySnapshot` 按月分区 |
| SKU 映射缺失（`sellerSku/fnsku` ↔ `productId`） | 补货引擎无输入 | P1 建 `ProductPlatformSku` 映射表 + 维护页，P2 前完成映射率 ≥ 95% |
| 多副本 + 进程内调度 | 重复拉单、429 | ADR-06 的 `SKIP LOCKED` 抢单 |
| 币种/汇率历史单据缺失 | 毛利不可比 | 迁移时补 `exchangeRate=1` 显式标记"未折算"，报表排除而非静默当 1 |
| 无 service 层，改造面广 | 回归风险 | 先抽 `InventoryService`，出库/入库/收货三条路径逐一替换，每替换一条跑一次账平校验 |

**必须先由业务确认的 5 件事**（架构无法替代）：
1. 现有 `Warehouse` 清单与"海外仓"边界（哪些算 `OVERSEAS`，哪些是 `PLATFORM_FBA`）。
2. 海外仓是否自有 WMS（`apiEnabled/apiKey/apiUrl` 字段暗示曾有此设想）——若有，第二期需加一个 `OverseasWmsAdapter`。
3. FBA 库存的权威口径：以 `available` 还是 `available + inbound` 作为补货可用量。
4. 补货决策的责任人（谁能 `APPROVED` 计划），决定审批流配置。
5. 平台订单是否需要进入 B2B 出库流程（若全部 FBA，则 `Order` 完全不用承载平台单，ADR-03 更彻底）。

### 1.2 三环节职责边界

| 层级 | 组件 | 职责 | 边界 |
|------|------|------|------|
| **采集层** | Chrome 插件 v2 | 用户手动单商品全字段采集（46字段） | 浏览器上下文，天然反检测 |
| **采集层** | Python 采集引擎 v2 | 批量店铺商品同步 + 关键词搜索 | 独立反检测策略 |
| **统一 API** | `/api/external/collect` | 接收采集数据、去重、写入 DB | 只关心 payload 结构 |
| **存储层** | CollectedProduct 模型 | 产品数据的结构化存储 | 7 个模型，211 行定义 |
| **梳理层** | 编辑页重构 v2 | 单页滚动式商品表单，采集→编辑→翻译→就绪 | 操作 CollectedProduct |
| **发布层** | 发布管线 + WooCommerce Publisher | 映射字段 → WooCommerce API | 276 行发布器逻辑 |

### 1.3 不变的部分（架构约束）

| 组件 | 原因 |
|------|------|
| API 层 payload 格式 | `POST /api/external/collect` 请求 body 结构不变，采集端填充更多字段 |
| CollectedProduct 模型 | 现有 7 个模型字段已覆盖阿里所有可采集字段 |
| WooCommerce 发布器核心逻辑 | `woocommerce-publisher.ts` 的 `buildProductData()` 和 `createVariations()` 逻辑可复用 |
| product/research pipeline | 采集端独立，不修改后续管线 |

### 1.4 变的部分（本次实现 + v1.1 补充）

| 组件 | 变化 |
|------|------|
| Chrome 插件提取引擎 | 完全重写为 ExtractionEngine 模式 |
| Chrome 插件 popup | 增加进度反馈、去重提示 |
| Python extractor.py | 增加变体/阶梯定价/detailData 提取 |
| Python store_collector_v2.py | 重写产品列表爬取逻辑 |
| Python export.py | 增强 payload builder |
| API 层 | 新增 `GET /check` 端点 + route.ts 补全字段 |
| **梳理后台编辑页** | **完全重构：5个Tab → 单页滚动式表单** |
| **WooCommerce 发布器** | **增加 supplier_info 元数据扩展** |
| **Arch 文档** | **补全数据流图、梳理设计、发布验证** |

## 7. 梳理后台编辑页重构设计

### 7.1 当前问题分析

**问题**：当前编辑页（`src/app/collected-products/[id]/page.tsx`，480行）使用5个Tab切分信息：

```
Tab 0: 基本信息（标题/价格/品牌/SKU/属性只读）→ 适合先看摘要
Tab 1: 描述与SEO → 编辑长文本
Tab 2: 图片管理 → 只看图片
Tab 3: 变体管理 → 查看变体
Tab 4: 发布记录 → 查看历史
```

**用户反馈的问题**：
1. **认知断裂**：编辑一个产品需要不停切Tab，无法获得产品全貌
2. **属性只读**：Tab 0 中的属性是 `<input readOnly>`，用户只能在采集后看到，无法编辑
3. **字段缺失**：物流信息（weight/l/w/h）、供应商信息、阶梯价格在Tab中无展示
4. **SEO 混淆**：描述和SEO放在一个Tab，但实际上描述是产品内容，SEO是营销元数据
5. **操作分散**：顶栏有保存/翻译/发布按钮，但发布状态要切到Tab 4才能看到

**参考设计**：阿里国际站发品页面是一张完整的商品表单，从上到下：
1. 标题/品牌/SKU（头部）
2. 产品图片（主图+图库，拖拽排序）
3. 价格信息（售价+阶梯定价表）
4. 规格属性（Key Attributes表）
5. 变体/规格（颜色/尺寸组合）
6. 详细描述（富文本编辑器）
7. 物流信息（重量/尺寸/运费分类/HS Code）
8. 供应商信息（展示已采集的供应商信息）
9. 认证信息（FDA/MSDS/GMP等）

### 7.3 页面布局设计要点

**核心原则：单页滚动，Section分隔，而非Tab切分**

| 设计决策 | 方案 | 理由 |
|----------|------|------|
| 页面结构 | 单页可滚动，9个Section按逻辑从上到下排列 | Tab切分导致认知断裂，单页可见产品全貌 |
| Section分隔 | 标题线 `═══ 名称 ═══` + 浅灰背景 + 左右留白 | 视觉上自然分组，无需Tab导航 |
| 右侧面板 | 300px 状态面板，sticky 定位 | 发布状态、采集时间、操作记录常驻可见 |
| 顶栏操作 | 固定高度，始终可见 | 保存/发布/翻译随时可用 |
| 字段编辑 | 所有字段 inline 可编辑，不再有 readOnly | 用户可直接修改采集数据 |
| 图片区域 | 网格展示 + 拖拽排序 + 主图标记 | 类似阿里发品页面的图片管理体验 |
| 属性区域 | 可编辑表格 + 添加行/删除行 | 全量属性可编辑，不再只读 |
| 响应式 | 大屏：左侧表单(2/3) + 右侧面板(1/3)；小屏：上下排布 | 兼顾宽屏编辑效率和小屏可读性 |

### 7.5 数据加载逻辑

#### 7.5.1 API 调用序列

```
页面加载时序:

1. GET /api/collected-products/:id
   → 返回完整 product + images + variants + attributes + publishLogs
   → 加载到 React 状态 (useState<ProductDetail>)

2. 表单变更时:
   → 本地状态更新 (updateField)
   → 不自动保存

3. 用户点击「保存」:
   → PUT /api/collected-products/:id
   → body: 完整 form 数据
   → 成功后刷新 form 状态

4. 用户点击「AI翻译」:
   → POST /api/collected-products/:id/translate
   → body: { fields: ['title', 'description', 'shortDescription'] }
   → 返回翻译后的字段值
   → 自动填充到 form 对应字段

5. 用户点击「发布到独立站」:
   → POST /api/collected-products/:id/publish
   → 自动转正 → WooCommerce API → 记录日志 → 更新状态
   → 刷新页面
```

#### 7.5.3 字段更新模式

```typescript
// 通用字段更新
const updateField = (field: string, value: any) => {
  setForm(prev => ({ ...prev, [field]: value }));
};

// 子表更新 (attributes/variants/images)
const updateAttribute = (index: number, field: string, value: string) => {
  setForm(prev => {
    const attrs = [...(prev.attributes || [])];
    attrs[index] = { ...attrs[index], [field]: value };
    return { ...prev, attributes: attrs };
  });
};

const addAttribute = () => {
  setForm(prev => ({
    ...prev,
    attributes: [...(prev.attributes || []), { name: '', value: '', unit: '', sortOrder: prev.attributes?.length || 0 }],
  }));
};

const removeAttribute = (index: number) => {
  setForm(prev => ({
    ...prev,
    attributes: (prev.attributes || []).filter((_, i) => i !== index),
  }));
};
```

### 7.6 与现有 WooCommerce Publisher 的联动

```
编辑页「发布到独立站」按钮
        │
        ▼
POST /api/collected-products/:id/publish
        │
        ▼
Publish API Route (publish/route.ts)
        │
        ├─ ① 检查 productId → 没有则自动转正（创建 Product 记录）
        ├─ ② 获取 WooCommerceConfig
        ├─ ③ 调用 new WooCommercePublisher(config)
        ├─ ④ 判断 create 还是 update (根据 woocommerceId)
        │
        ├─ [create 路径]
        │   ├─ WooCommercePublisher.create(product)
        │   │   ├─ buildProductData(product, false)
        │   │   │   ├─ name = product.titleEn || product.title
        │   │   │   ├─ type = variants.length > 0 ? 'variable' : 'simple'
        │   │   │   ├─ description = cleaned HTML
        │   │   │   ├─ regular_price = String(product.price)
        │   │   │   ├─ sale_price = String(product.compareAtPrice)
        │   │   │   ├─ weight = String(product.weight)
        │   │   │   ├─ dimensions = { length, width, height }
        │   │   │   ├─ images = uploadImages() → [{ id, position }]
        │   │   │   ├─ attributes = extractVariantAttributes(variants)
        │   │   │   └─ meta_data = [
        │   │   │       { key: '_collected_from', value: source },
        │   │   │       { key: '_collected_source_url', value: sourceUrl },
        │   │   │       { key: '_supplier_info', value: JSON.stringify(supplier) } // ★ 新增
        │   │   │     ]
        │   │   └─ POST /wp-json/wc/v3/products
        │   │
        │   └─ 如果有变体:
        │       └─ createVariations(body.id, product)
        │           └─ 逐个 POST .../products/{id}/variations
        │               ├─ sku, regular_price, attributes (option映射)
        │
        ├─ [update 路径]
        │   └─ WooCommercePublisher.update(product)
        │       ├─ buildProductData(product, true)  // isUpdate=true, 不传图片
        │       └─ PUT /wp-json/wc/v3/products/{woocommerceId}
        │
        └─ ⑤ 记录 PublishLog
        └─ ⑥ 更新 CollectedProduct: pipelineStatus='published'
```

**关键联动要点**：
1. 编辑页修改的字段通过 `PUT /api/collected-products/:id` 保存到 CollectedProduct
2. 发布时读取的是 **已保存的 CollectedProduct 数据库记录**，不是表单的 React 状态
3. 因此发布前必须先保存（当前实现就是如此：点击发布 → 触发保存 → 再调用发布API）
4. 编辑页重构不需要修改 WooCommercePublisher 的核心逻辑
5. 唯一需要扩展的是：在 `meta_data` 中增加 `_supplier_info` 字段

### 8.2 需要扩展的发布逻辑

#### 8.2.1 供应商信息 → meta_data (P0)

当前 `buildProductData()` 已生成 `meta_data` 数组，只需增加一条：

```typescript
// 在 buildProductData() 中新增
if (product.rawData?.supplier) {
  data.meta_data.push({
    key: '_supplier_info',
    value: typeof product.rawData.supplier === 'string'
      ? product.rawData.supplier
      : JSON.stringify(product.rawData.supplier),
  });
}
```

#### 8.2.2 非变体属性 → meta_data (P1)

阿里采集的属性（成分、功效、容量等）不能直接映射到 WooCommerce，因为 WooCommerce 的 `attributes` 字段是为变体服务的。建议存入 `meta_data`：

```typescript
// 在 buildProductData() 中新增
if (product.attributes?.length > 0) {
  data.meta_data.push({
    key: '_product_attributes',
    value: JSON.stringify(product.attributes.map((a: any) => ({
      name: a.name,
      value: a.value,
      unit: a.unit,
    }))),
  });
}
```

也可以在 WooCommerce 端创建真实的 Attribute 条目（非变体属性），在后台「Additional Information」中显示。但这需要 WG 的 `attribute` API 先注册属性。建议先走 meta_data，后续再考虑原生方式。

#### 8.2.3 HS Code → meta_data (P1)

```typescript
if (product.hsCode) {
  data.meta_data.push({ key: '_hs_code', value: product.hsCode });
}
```

#### 8.2.4 运费分类 → shipping_class (P1)

WooCommerce 的 `shipping_class` 需要先在 WooCommerce 后台创建 Shipping Class，然后传其 ID 或 slug。当前实现简化为 meta_data：

```typescript
if (product.shippingClass) {
  data.meta_data.push({ key: '_shipping_class', value: product.shippingClass });
}
```

#### 8.2.5 库存 → stock_quantity (P0)

```typescript
// 在 buildProductData() 中新增
if (product.stockQuantity !== null && product.stockQuantity !== undefined) {
  data.stock_quantity = product.stockQuantity;

}
```

### 8.3 阶梯定价→WooCommerce 策略

| 阶梯定价场景 | price (regular_price) | compareAtPrice (sale_price) | 说明 |
|-------------|----------------------|---------------------------|------|
| 无阶梯价，单一定价 | product.price | product.compareAtPrice | 直接传递 |
| 有阶梯价，≥2档 | tieredPricing[last].price (最低价) | tieredPricing[0].price (最高价) | 最低价设售价，最高价设划线价 |
| 有阶梯价，仅1档 | tieredPricing[0].price | null | 只用该价格 |

**WooCommerce 实际展示效果**：
- 用户在独立站看到：~~$15.00~~ **$10.00** (划线表示原价)
- 但无法展示阶梯定价表（如 "100+个 $12.00"）
- 解决方案：在 description 末尾附加一段阶梯定价文字说明

### 8.4 变体→WooCommerce 映射详解

```
CollectedProductVariant               WooCommerce Variation API
─────────────────────                 ──────────────────────────
{                                      {
  sku: "R-S-M",             ─────→      "sku": "R-S-M",
  price: 15.00,                         "regular_price": "15.00",
  stock: 100,                           "stock_quantity": 100,
  options: [                            "attributes": [
    { name: "颜色", value: "红色" },       { "name": "颜色", "option": "红色" },

同时 Parent Product 需要 attributes 描述变体维度:
{

    { "name": "颜色", "options": ["红色", "蓝色", "白色"], "variation": true },

  ]
}
```

**当前 `extractVariantAttributes()` 实现已正确**：从所有 variant 的 options 中提取唯一 name+values 组合。

### 8.5 图片→WooCommerce 映射详解

```
CollectedProductImage                    WordPress Media → WooCommerce Image
─────────────────────                    ────────────────────────────────────
{                                        1. Buffer.from(base64)
  data: "base64...",      ─────→        2. POST /wp-json/wp/v2/media
  mimeType: "image/jpeg",               3. return { id: media.id, position: sortOrder }
  fileName: "product_1.jpg",

}                                        5. 其他 → images[1..n].position=sortOrder

WooCommerce 产品 API:
{
  "images": [
    { "id": 123, "position": 0 },    // 主图 auto-detected by position=0
    { "id": 124, "position": 1 },    // gallery 图
    { "id": 125, "position": 2 }     // gallery 图
  ]
}
```

**当前 `uploadImages()` 实现已正确**：base64 → Buffer → Blob → WordPress Media API → 返回 id。

## 附录 B: 组件目录结构建议

```
为了保持项目组织一致性，建议将梳理后台编辑页组件放在：
src/components/collected-product/edit/

而不是：
src/app/collected-products/[id]/components/

理由：
- Next.js App Router 的 app/ 目录应只放页面级文件（page.tsx, layout.tsx）
- 可复用组件应放在 src/components/ 下
- 与现有项目模式一致（已有 src/components/ui/ 等）
```
